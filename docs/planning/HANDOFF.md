## 2. 本批做了什么（含「为什么这么做」，避免下一棒改回去）

### 2.1 DPI 深度包检测（`fb031ef`）

**动因是用户的一句话**：「pcap 这个流量一大就不行了」。实测证据：
`src/backends/pcap_file.cpp` 在 open 时把**整个文件**读进
`std::vector<PacketBuffer>` —— 非流式、无界内存、不报丢包，省网 100G 物理上走不通。
本轮补的是**识别能力**这一侧（真正的流式采集属另一个任务）。

新增 `src/dpi/`，核心是**三级递进识别框架**：
端口给候选顺序（成本 0）→ 载荷特征逐个确认 → 兜底 unknown。

**四个必须延续的设计决定：**

1. **裁决语义用四态枚举，刻意不用 `Result`**
   `Identified / NeedMore / Malformed / Unknown`。
   理由：「不是我的协议（Rejected）」与「我的协议解析坏了（Malformed）」
   在 `Result` 里都只是 `Err`，下游无法区分该**等分片**还是该**丢弃**——
   这正是省网 unknown 率虚高的主因（坏包被计入"再等等就能识别"的桶里，
   而它永远等不出结果）。框架层 `Malformed` 优先于 `NeedMore`。

2. **只看首包、不重组**（本层是纯函数）
   省网要在连接建立后几百微秒内出结果，等流拼完整 SLA 已过。
   代价是被切开的首包判 `NeedMore` —— 由重组层补（见 2.2），**不改解析器**。

3. **GREASE 必须剔除**（RFC 8701，`0x0a0a` 等 16 个值）
   否则 JA3 对同一客户端产出不同指纹，指纹库直接失效。数值段用**十进制**
   （`0x1301` → `4865`），空段留空（`771,,,,`）。

4. **零第三方依赖**：MD5 自实现（JA3 需要）。
   不是为了洁癖 —— 是为了保持「离线可构建、工具链可验证」。

### 2.2 TCP 乱序重组（`4d62530`）

**动因**：DPI 的 `NeedMore` 需要有价值，「补字节的人」就是这一层。

新增 `src/reassembly/`，五个文件各担一件事：

| 文件 | 职责 | 关键约束 |
| --- | --- | --- |
| `seq.rs` | 32 位序号回绕算术 | 10G 链路跑满约 **3.4 秒**就绕一圈——回绕不是边界情况而是必现 |
| `intervals.rs` | 有序区间集 | 三条不变式：按 start 严格递增 / 互不相交 / 互不相邻 |
| `stream.rs` | 单向流 | 内存上限按**保连续弃乱序**降级 |
| `tcp.rs` | 头与选项解析 | TLV 长度越界即**停止**解析，不"跳过继续" |
| `tests.rs` | 向量驱动断言 | 向量 `include_bytes!` 编进二进制 |

**四个必须延续的设计决定：**

1. **重叠仲裁默认 `KeepOld`（Linux `tcp_trim_head` 语义）**
   含义是「流的内容一旦定下就不再被后续报文改写」。旁路设备要复现的是
   **接收端真实收到的字节流**，而不是攻击者最后重发的那个版本。
   代码里同时提供 `KeepNew`（BSD），因为两种语义真实存在且**行为相反**，
   必须显式选择而不是隐式固定。

2. **`anchored_by_syn` 标志必须保留**
   抓到 SYN 才锚 ISN+1；旁路中途接入时以首个数据段锚定，此时该标志为 `false`。
   用途是让下游能看见「这条流的开头完整性未知」——若抹掉这个区别，
   「开头不完整」会被静默当成「开头就是这个字节」。

3. **内存上限的降级方向是「保连续、弃乱序」**
   上限触发时，能推进连续前缀的段照收（马上会被交付并释放），
   只会加深空洞的段丢弃。这样即便在攻击流量下，DPI 依然能在流的开头拿到
   完整前缀并出结果——退化了但没瞎，比"整体停摆"有用得多。

4. **与 DPI 的衔接只有一处**：`Stream::identify_app()`
   把重组后的连续前缀喂给同一个纯函数 `dpi::identify`。
   若发现需要为重组改 DPI，说明分层串了。

### 2.3 顺带修掉的真实缺陷

| 缺陷 | 表现 | 根因 |
| --- | --- | --- |
| MD5 初值 B 写错 | 全部 JA3 指纹错误 | `0xEFCD89AB` 应为 `0xEFCDAB89`（**三个独立实现都错在同一处**，靠移植到 Python 与 `hashlib` 逐步比对才定位） |
| MD5 摘要字节序反 | 32 字符、外观合法、每两字符都反 | 应逐 u32 按小端字节输出 |
| MD5 第 3 轮 G 表抄错 | 摘要全错 | 正确为 `5,8,11,14,1,4,7,10,13,0,3,6,9,12,15,2` |
| TLS 握手长度位置错 | 得出荒谬的 `0x010000` | 是 **3 字节**且从**偏移 6** 起（不是 2 字节从偏移 5） |
| `Cursor` 起始偏移漏 9 | 每个字段都错位 | 握手体起点偏移 9 |
| 扩展体长度头被当列表元素 | JA3 里多出来路不明的小数字 | SNI / `supported_groups` 有 2 字节长度头；`supported_versions` 是 **1 字节** |
| 生成器畸形样本其实合法 | 测的是空气 | `tls-bad-inner-len` 偏移漏算 4 字节握手头，改坏的是 random |
| SACK 选项长度算成 `8n` | SACK 块解析不出 | 应为 `8n+2`（含 kind 与 len 两字节） |

### 2.4 从「能识别」到「能产出记录」（本批）

链路补齐为 `Packet → FlowTable → Session → FeatureExtractor → FlowRecord`，
新增离线 CLI `cythsec-analyze -r x.pcap -o flows.jsonl`（CYS-TRF-035）。

**几个刻意定下来的语义，别改回去：**

1. **`fwd`/`rev` 是「规范端点序」，不是「发起方/响应方」。** 规范序保证同一会话
   无论方向都落到同一个键（CYS-TRF-005）；「谁是发起方」是**另一个**字段
   (`tcp.initiator`，取 SYN 的方向)。把两者混用，下游就会把「方向」当「角色」用。
2. **TCP 事件判定要吃「段载荷长度」，不是 IP 载荷长度。**
   `Packet::payload_len` 是 IP 载荷（含 20 字节 TCP 头），`TcpEvent::classify`
   要的是**去掉头之后的**字节数。本批修掉的真实缺陷就在这里：用含头长度判定，
   每个纯 ACK（IP 载荷 20、数据 0）都被算成 `Data`；容忍模式下碰巧仍能走到
   `Established`/`TimeWait`（**所以旧测试全绿**），严格模式下则卡在 `syn_received`
   且 `FinWait2`/`CloseWait`/`LastAck` 永不可达。修法是把两个量**显式分成两个参数**
   (`TcpObservation{flags, l4_payload_len}`)，而不是在调用处随手减 20 —— 后者下一个人
   一定会漏。
3. **`app.outcome = "not_inspected"` 不能并进 `"unknown"`。** 「没看」和「看了不认识」
   在统计上后果相反：前者是我们没覆盖，后者是流量本身不成形。
4. **熵在聚合直方图上算，`0` 有两种含义**（无字节 / 全部相同），用 `bytes` 列消歧。
5. **`schema_version` 随任何列变更抬版本**；`risk_score` 在 CYS-TRF-031 之前恒为 `null`
   （宁可留空，也不要先填一个假分数进存储）。

**新增的第三方门禁（`--flows`）**：`scripts/verify/check-flow-records.sh` 用 tshark
独立解析样本，逐流核对 **927 项**（会话集合 / 包数字节数 / 双向计数 / 方向切换 /
首末时间戳 / TCP 末态 / 发起方 / 中途接入 / 应用识别 / 解码失败计数 / 统计自证）。
两个关键设计：

- **TCP 末态用第二实现判定**：拿着 tshark 给的标志位序列，按规则表**重新推**一个末态，
  而不是去抄 Rust 的迁移表 —— 抄表等于让实现给自己打分。规则覆盖不到的组合打印
  `SKIP` 并**不计入通过**（当前 7 项，全部附理由）。
- **反向故障注入是默认行为**：17 项篡改（改包数、改状态、翻转发起方、改 tshark 事实、
  改自家 stderr 摘要、删/重复会话、空输入……）必须**全部被检出**，否则判红。
  理由见 §4.2：核验器自己写错时，「绿色的通过」和「绿色的没跑」完全一样。

**顺带修正一处过期期望**：`--e2e` 里硬编码「5 个报文」，新增
`datasets/pcap/sample-session-tcp.pcap`（18 帧）后如期报红（5 → 23）。
已改成可逐项复核的分解式（`4+1+18` 帧 / `4+1+9` 流 / 1 个非首片分片），
并把「这组数字是活的、改样本集必须同步改」写进注释 —— 期望值过期就该红，
不该顺手删掉那条断言。

### 2.5 数据面基准：先用需求推导出目标值，再量（本批）

`CYS-TRF-006/007` 此前卡在两条**指标**上（「1M 并发流插入基准达标」「无内存增长」）。
本批补上基准，但**没有**按原计划引 Criterion —— 本工程硬约定是零第三方依赖 +
`--offline` 可构建，基准工具不该是例外。代价写清楚：**只报点估计**（每项跑两遍、
取第二遍，两遍都打印），没有离群值剔除、置信区间与自动跨 commit 比对。

**`src/bin/bench.rs`（二进制 `cythsec-bench`）的四个设计决定**：

1. **目标值由工作量需求推导，不是"跑一遍记下来"**：
   10Gbps 最坏包速率 = `10e9 / (84×8)` = **14.88 Mpps**（84B = 64B 最小帧 + 7B 前导 +
   1B SFD + 12B 帧间隙；按 64B 算会得到 19.53 Mpps，那是自己给自己放宽要求）；
   1M 条超时扫描 ≤200ms（秒级节拍留 5 倍余量）；TCP 重组 ≥1.25 GB/s（10Gbps 净载荷）；
   **新建流速率单独算**：1M 容量 / 60s 瞬态超时 ≈ 17k 次/s，取 1 Mops/s 作 60 倍余量 ——
   拿包速率（14.88 Mpps）去要求"插入新流"是口径错误，会把正常的东西判成不合格。
2. **两类阈值分开**（本批最重要的设计）：`需求目标`回答"够不够用"，`回归下限`回答
   "这版有没有把上一版跑坏"。默认退出码只看后者，`--require-targets` 才按目标判定。
   混成一个码，人会分不清该修哪个；而且当前有 8 项未达目标，若它们都让门禁变红，
   门禁会天天红，红到没人看。
3. **回归下限余量刻意留大（≥2×）**：实测同机连跑两次，稳态查表类能差 20~30%
   （散热 / 其它负载 / 内存布局）。5% 余量的门禁只会变成随机假红，而随机红等于没有门禁。
4. **判定逻辑只有一处**（`Case::passed/regressed`）：表格显示、汇总行、退出码都调它，
   避免"表格说达标、退出码按另一套规则算"这种最隐蔽的自相矛盾。

**首轮就抓出三处，其中一处当场修掉**：

| # | 发现 | 证据 | 处置 |
| --- | --- | --- | --- |
| 1 | `expire()` 把全部到期条目搬进 `Vec<FlowEntry>`（每条 432B）排序后派发 | 250k 条「填满→全到期」每轮 RSS **+99MiB** 且不保证回落（逻辑活跃条目恒为 0）；对照实验（只 insert+drop / insert+`clear()`）RSS 平稳，`HashMap` 自身 churn 也平稳，故不是分配器通病 | **已修**：只收**键**（40B/条），按全局键序逐条删除并派发。回调顺序（全局按键升序）与逐出语义不变；RSS +99→**+6MiB/轮**，扫描 **1.62→2.50M 条/s**。唯一可观察差异：回调期间表里可能仍留有尚未派发的到期条目（旧实现先删完再派发）—— 已在源码注明并接受，补 2 个测试钉住 |
| 2 | `evict_lru` 每次逐出**全扫分片**，成本 O(每分片容量) | 每片容量 256 → **1.09µs/次**；8192 → **52.2µs/次**；容量 32× → 耗时 52× | **已修（2026-10-04 第二段）**：分片内改用**槽位数组 + 双向链表**维护活动序（插入挂尾、命中移尾、逐出摘头），语义仍是**精确 LRU**、仍确定性，代价 O(1)：256 → **0.21µs/次**、8192 → **0.34µs/次**，容量 32× → 耗时 **1.6~1.8×**。旧路径保留为 `EvictPolicy::LruScan` 作对照，并新增 `stats().evict_candidates`（链表策略恒 0、扫描策略 = 每片容量 × 逐出次数）把复杂度变成**可测断言**。**先评估并实测否掉了采样 LRU**：Redis 式 K=8 采样在「400 流 / 128 槽位 / 90% 热点」负载上热点命中率只有 **58.4%**，精确 LRU 是 **99.9%** —— 流被逐出又重建意味着同一条会话的记录被切成两段，这个代价换不来那点 CPU |
| 3 | 稳态查表够不上 10G 最坏情况 | update **5.6~8.6** / query-hit **5.0~6.9** / query-miss **13.8** Mops/s，需求 14.88（达成 34~58%）；每流实测 **0.97KB**（槽位 448B + 键表约 50B + IAT 环形 512B） | **已定位并选定路线**（2026-10-04 第三段，见 **§2.6**）：多实例分核实测 **2 核压线、4 核留 1.5~1.8 倍余量** → 核预算 **4 核/10G 口**；热/冷字段拆分**暂不做**（触发条件写在 §2.6）。**连带发现**：`FlowTable` 原先不是 `Send`（观察者 `Box<dyn FlowObserver>` + 测试用 `Rc`），"每核一张表搬进 worker 线程"根本无法表达 —— 已改为 `Box<dyn FlowObserver + Send>` 并加编译期断言。**本批的副作用**：O(1) LRU 让插入快一倍（0.98→2.06 Mops/s）、逐出快 5~150 倍、单表内存减半（2390→970 B/条，全新进程同配置实测），代价是命中路径多一次间接寻址 —— query-hit 7.68→5.02 Mops/s（−35%），update 在噪声内（5.71→5.59） |

**顺带修正两处我自己上一批写错的事实**：分片容器写成 `BTreeMap`（实为
`HashMap` + FNV-1a，确定性顺序来自显式排序）；`FlowStats` 包长直方图写成"256 桶"
（实为 **12 个 log2 桶**；256 桶是 `feature::ENTROPY_BINS`，两者不是同一个东西）。

**第二段（2026-10-04 收口批次）还改掉了一处**判据本身**的错误**：`table-steady-memory`
原先拿「填充后 → 灌完 5× 容量」作差。条目内嵌的 IAT 环形缓冲是 512B/条，填充时每条只写过
第一个元素，剩下 63 个槽位的**页**要等后续包才被触碰 —— 第 1 轮的 RSS 会一次性抬高一个与
容量成正比的量（1M 条时 **+206MiB**），第 2 轮起完全平；那是"页第一次被触碰"，不是"内存随
流量增长"。旧写法把这个一次性项算成增长，判据本身是错的（旧实现凑巧为 0，只因它前面的用例
刚好触碰过同尺寸的页）。现在**预热一轮不计入判定**、逐轮记录 RSS、取"预热后各轮增量最大值"，
并整条打印原始序列（含预热轮，不藏）。修正后两版都判 0.00 MiB。

### 2.6 稳态吞吐与 10G 的差距：先量再决定（2026-10-04 第三段）

`CYS-TRF-006` 卡在「每包路径吞吐只有 14.88 Mpps 需求的 34~38%」。HANDOFF §8 第一梯队第 1 项
的要求是：**先做便宜实验（每核一张独立表，证明近线性扩展），再决定走「多实例分核」还是
「条目拆热/冷字段」—— 不要在没有数据的情况下重构流表**。

**实验**（`cythsec-bench` 新增 6 个判据项，细节见 `bin/bench.rs` 头部「多实例分核实验」）：
N 张**完全独立**的 `FlowTable` 各占一个线程跑稳态 update；外加两条对照 ——
**纯计算对照**（同线程数、同操作次数，只做寄存器运算）用来量出「**这台机器本身**的多线程
上限」，**小工作集对照**（每实例 2000 条 ≈ 3MB，能进每核 L2）把「访存/工作集」这个因素单独
拎出来。

实测（Apple M1 Pro / 10 逻辑核 / release / 每实例 12.5 万条 / 多次运行）：

| 线程数 | 聚合吞吐 | 每线程 | 扩展效率 |
| --- | --- | --- | --- |
| 1 | 6.9~8.6 Mops/s | 6.9~8.6 | 1.00 |
| 2 | 13.4~15.3 | 6.7~7.6 | 0.82~0.96 |
| 4 | 22.6~26.2 | 5.6~6.5 | 0.71~0.95 |
| 8 | 28.0~34.8 | 3.5~4.4 | 0.42~0.63 |

**决定：走「每核一张独立表」（多实例分核），热/冷字段拆分暂不做。**

- **2 核压线达标，4 核留 1.5~1.8 倍余量** → 核预算 = **4 核/10G 口**
  （判据项 `table-cores-for-10g`：取「最小档位使聚合 ≥1.5×14.88Mpps」，1.5× 是留给同核上
  其它环节的工程余量）。
- **8 线程不再近线性，但不是表内的共享瓶颈**：同一台机器上的纯计算对照也只有 0.54~0.73；
  小工作集对照的每线程吞吐比大工作集高 34~67%，但仍只有它自己单线程的 0.4~0.5 倍。
  即**机器级并发上限是主因、访存是次要因素**。判据因此用**比值**（流表扩展效率 ÷ 纯计算
  对照扩展效率）：实测 0.55~0.92，目标 0.5（要求「同量级」，判据要拦的是塌到 0.1 量级的
  共享瓶颈）、下限 0.25；串行注入档实测 0.06~0.10，判红。
- **热/冷字段拆分不作当前路线**：核预算（4）远小于常见机型核数，拆条目是「省核」才需要的
  优化，却要动条目内存布局、分片、超时与回调一整套。**触发条件**：目标机型核预算 < 所需
  核数，或单表规模再涨一个数量级、cache miss 成为主导。
- **前提是顺带发现的**：`FlowTable` 原先**不是 `Send`**（观察者是 `Box<dyn FlowObserver>`，
  测试实现还用 `Rc`）—— 「每核一张表 + 把表搬进 worker 线程」这条路**根本无法表达**
  （bench 直接编译失败）。已改为 `Box<dyn FlowObserver + Send>`（只要 `Send`、**不要**
  `Sync`：表不需要被多线程共享引用，「共享一张表 + 加锁」恰是要避免的形态），并加编译期断言
  `table_is_send_so_it_can_move_to_a_worker_thread` 守住。

**本实验不回答的**：整条每包流水线的核预算 —— 特征更新、会话归属等环节各有自己的
14.88 Mpps 目标（实测 4~7 Mops/s），要各自核算之后才能给出一个 10G 口的**总**核预算。
**§2.8 已接着回答了这条**（离线路径）：接线完成后整条流水线实测 0.918 Mpps/核、
8 核封顶 2.53×，上限是**派发端**而不是流表 —— 即"加核"在离线架构上解决不了总核预算。

**反向注入（判据的判据）**：`--inject-serialized-scaling` 把并行档换成「所有线程抢一张表 +
互斥锁」，要求扩展性判据判出退步并退出非零。单测 `serialized_table_is_flagged_as_not_scaling`
（真表真锁、真线程）与门禁 `check-flow-bench.sh` 的第 4 项注入都跑它 ——
**一个只会说「扩展性良好」的判据等于没有判据**。

### 2.7 换机器验证：Linux aarch64 测试机（2026-10-05）

**为什么做**：此前所有验证都只在 macOS/M1 Pro 上跑过。仓库宣称支持的发行版里有

本批把开发机（VMware Fusion 上的 Rocky Linux 10.2 aarch64 虚拟机，2 vCPU / 3 GB /
4 KiB 页）接进回路，用它当**第二台机器**。（机器信息与接入方式见
`.workbuddy/memory/MEMORY.md` 的「测试环境」；凭据不入仓库。）

**做法**：`git archive HEAD` 同步源码（**不用** `tar --exclude`，见 §7 第 9 条），
装上与本机**逐位相同**的 `rustc 1.97.1`（+ gcc 14.3.1 / tshark 4.4.2）后跑同一套脚本。

**结果（全部通过）**：

| 关口 | 结果 |
| --- | --- |
| `test-all.sh --rust` | **337 项全过**，与本机计数一致 |
| `test-all.sh --cpp` | **6/6 通过** |
| `test-all.sh --live` | **13/13 断言**（该关口此后加了「裁判口径自证」，现为 **14 项**）：真实网卡 `enp2s0` 采集 74 包、`tshark` 复核帧数 74 = 落盘数、环内消费 74 = 灌入数、解出 10 条 Flow、Rust `decode_fail` 与 tshark 前缀非 IP 帧数同为 0（三实现判定一致） |

**换机器才暴露的 3 处「把本机/平台假设当成普遍事实」（全部已修 + 已加自证）**：

1. **`test-all.sh` 的工具链预检不看选了哪些分组** —— `--rust` 也要求 cmake/go/node，
   在只有 cargo 的机器上直接报「工具链缺失: cmake」而**本次运行根本不需要它**
   （在虚拟机上是实测撞到的：先卡 cmake，装完 cmake 又卡 go）。改为按所选分组取工具链
   （纯函数 `required_tools()`，便于自证），并在 `--self-test` 里加**反向注入**：
   PATH 中没有 cmake 时 `--rust` 必须通过、`--cpp` 必须点名判红。
2. **`bench.rs` 的串行档断言带机器属性** —— `serialized_table_is_flagged_as_not_scaling`
   断言「串行效率 < 回归下限 0.25」，10 核实测 0.05~0.10 成立，**2 核上是 0.33**（核太少，
   表达不出抢锁），于是这条判据自己变成假红。改为机器无关形态：**永远**断言
   `串行效率 < 并行效率`；只有 `ap ≥ 4` 才断言比值低于下限；另加与核数无关的兜底
   （串行档**顶档聚合**必须低于该档下限 —— 共享锁的特征就是"多核也上不去"）。
   两机复验：10 核 13/13、2 核 13/13。
3. **C++ 实时采集测试里写死了两处平台常量** —— ① 用 `0xFFFF` 当「未知链路类型」：
   macOS 上确实未知，**Linux 上它是具名的 `ARPHRD_VOID`**（相邻 `0xFFFE` = `ARPHRD_NONE`），
   于是实现照实返回 `VOID`、断言判红；改用 `0x10000`（超出 16 位 `ARPHRD_*`/`DLT_` 空间），
   且期望的十六进制回显**由常量算出**。② `kNoSuchIface` 是 32 字符，而 `IF_NAMESIZE`=16，
   Linux 的 `open()` 会**先命中「接口名过长」分支**，报的不是「不存在」，于是
   「诊断必须给出可操作线索」这条断言在 aarch64 上红；改用短名（"超长名字不崩溃"本就有专门用例）。
   两机复验：macOS 6/6、Linux 6/6。

**这三条都不是「Linux 有 bug」，而是测试里写死的机器/平台假设** —— 换一台机器跑一次全暴露，
且**全都是假红**（把机器属性报成代码缺陷），正是本仓库最反对的那类红。教训与本仓库一贯口径一致：
**阈值与常量一旦带平台或机器属性，判据要么改成相对量，要么显式限定适用条件。**

**顺带修掉一处默认门禁的潜伏假红（同样是换环境才暴露）**：`--live` 的 D 项断言「Rust 的 `decode_fail` == tshark 判定的前缀非 IP 帧数」原先用 `tshark -e eth.type` 取数，而**网桥周期发的 STP BPDU 是 802.3 + LLC 帧**（`eth:llc:stp`，用长度字段而非 EtherType）→ `eth.type` 输出空行 → 旧写法 `awk 'NF {...}'` 把空行**整行丢掉** → 裁判少数 6 帧，把「两个实现一致判 6、裁判判 0」报成不一致。**只要网络里有交换机在发 STP，这道默认门禁就会长期假红**（本机 en0 上实测 6 帧；此前各批「13 项全过」只是因为抓包窗口里恰好没有 LLC 帧，虚拟机那次是 0==0 空过）。修法：裁判改用 `frame.protocols`（协议栈里没有 ip/ipv6 即非 IP，与解析器口径一致且对任何封装都成立，抽成 `nonip_count()` 并写明为什么不用 `eth.type`），不一致时把三方计数与错误码明细一起摊开便于归因。修后本机 8==8、虚拟机 0==0。并且**把这条口径做成每次都会跑的自证**：合成一个「1 帧 LLC/STP + 1 帧 IPv4」的两帧 pcap，断言裁判只数出 1 帧非 IP（旧口径在此立刻红：0 != 1，已用反向注入实测确认），python3/tshark 缺席时显式打印「未核验（不计为通过）」。这道关口因此从 13 项变为 **14 项断言**。

**同一个位置的第二次假红（2026-10-05，另一类）**：口径改成 `frame.protocols` 之后**仍会假红**，
这次是**非首片分片**：归因行给出 `ring-consume decode_fail code=decode.non_initial_fragment count=2`，
而 tshark 的 `frame.protocols` 对非首片分片照样写 `eth:ethertype:ip`（端口在首片里，它只能看到那么多层）
→「非 IP(56) vs decode_fail(58)」差 2，抓包窗口里一出现分片这道默认关口就红。
**病根与上一次完全相同：判据里藏了一个依赖现场流量的隐藏变量**（所以表现都是"偶尔红"）。
修法：裁判口径从「非 IP」改成「解不出五元组」= 非 IP + IPv4 非首片(`ip.frag_offset > 0`) +
IPv6 非首片(`ipv6.fraghdr.offset > 0`) —— 三类都是**按设计拒绝**（没有端口就没法组五元组），
不是缺陷。并且把"靠运气才能复现"变成**确定性自证**：每次跑都用合成 3 帧
（LLC/STP + IPv4 + IPv4 非首片）灌共享环跑**完整判定链**，要求 `decode_fail == 裁判口径 == 2`。
这道关口因此从 14 项变为 **15 项断言**。

**这次修法本身给出的两条教训**（比结论更重要）：
① 夹具里 IPv4 首部少写一个字节，`flags+frag` 字段就被顶偏、合成帧退化成首片 ——
   是**独立的期望值**（"裁判必须判 2"）当场抓到的；而"完整判定链"那条因为"两边一起瞎"
   （裁判与解码器都判 1）**照样通过**。所以**"两个数相等"永远不能单独当自证**：
   至少有一个数必须来自与被测对象无关的期望值。
② "两个独立实现判定不一致" ≠ "有一方错了"。先把**按设计拒绝**的类别逐条枚举进裁判口径，
   再谈一致性 —— 否则这条断言随时会因为现场流量变化而红，而红的原因与被测代码毫无关系。

**能力边界（诚实）**：该机 2 vCPU，**吞吐类结论不可用**（`--bench` 只 `--report-only`，
照门禁阈值跑会红 —— 阈值是机器相对的，不得据其判红）；页大小是 **4 KiB**
（`CONFIG_ARM64_4K_PAGES=y`），与 macOS 的 16 KiB 不同、对 `af_packet.h` 的 PAGE_SIZE
运行时假设仍有覆盖价值，但**「64 KiB 页路径」至今没有覆盖环境**（早前文档把它写成 64 KiB 是错的，已改）。

### 2.8 把「每核一张独立表」接进消费路径：`cythsec-analyze --workers N`（2026-10-05 第二段）

**为什么做**：§2.6 只证明了**流表**能扩展，而流水线本体（`cythsec-analyze`）当时仍是单线程
单表。"路线定了"与"接上了"之间隔着一次真正的改造，而这次改造的主要风险不是性能、是
**正确性**：并行一旦改变了结论，所有历史输出与门禁基线的可比性都会一起失效。

**做了什么**（`dataplane/traffic-engine/src/pipeline.rs` + `src/bin/analyze.rs`）：
- 抽出 `PipelineState`（私有流表 + 会话 + 特征 + DPI 探针），**每包路径只有一份实现**，
  就地模式与分片模式共用（各写一份必然漂移，而漂移的表现恰好是"单线程与多线程不是一回事"）；
- `analyze_pcap_with(reader, opts, workers)`：`workers=1` 走**就地**路径（与历史行为逐字一致，
  不引入哈希/信道/线程开销）；`workers>1` 静态分片 → 每 worker 一个线程、各持私有状态，
  **无锁、零共享**；
- CLI 加 `--workers N`（默认 1），统计里报 `workers=`、每个 worker 承担多少条流、
  以及分片模式的限制（`evicted=`）。

**两条关键设计**（写下来是为了下一棒不要"顺手简化"掉）：
1. **分片按 `key.canonical()`**：按原始五元组分片会把一条会话的两个方向分到不同 worker，
   两边各建一套状态 —— 记录数翻倍，而**不会报错**。
2. **会话 id 由派发端按"首次出现顺序"统一分配**：worker 各自编号会互相冲突、且随分片结果
   变化；派发端看到的是同一个包流，所以它给出的 id 与 worker 数无关 —— 这正是"逐字节一致"的来源。

**量出来的数字**（`bash scripts/verify/bench-pipeline.sh 888000 3`：M1 Pro / 10 逻辑核 /
release / 91.4 万包 / 271 MB / 页缓存热；**脚本不做阈值判定**，机器相关）：

| worker | 用时 | 吞吐 | 加速比 |
| --- | --- | --- | --- |
| 1 | 0.996 s | 0.918 Mpps | 1.00 |
| 2 | 0.667 | 1.370 | 1.49 |
| 4 | 0.403 | 2.268 | 2.47 |
| 8 | 0.393 | 2.328 | **2.53（上限）** |
| 16 | 0.400 | 2.284 | 2.49 |

**上限归因（本节的结论）**：加速比在 8 个 worker 上封顶 2.53×，平台值 0.393 s 就是
**派发端**（读盘 + 解帧 + 分片 + 入队）的耗时 → 派发端上限 **2.33 Mpps**，worker 侧总工作量
0.603 s。**离线路径的并行上限是派发端，不是流表**：再加核只是让派发端更忙（16 档已回落）。
对"10G 口**总**核预算"的回答因此是：按本次混合负载（平均 297 B/包、含 DPI/会话/特征），
整条流水线上限 2.33 Mpps ≈ 10G 最坏帧（64 B / 14.88 Mpps）的 **16%**，而且
**这部分差距不能靠加核解决**。要线性只有一条路：让"读包 + 解帧"也分掉 ——
每队列一个环、每个 worker 自己读自己的环（`CYS-PKT-009`），那时连派发端都不需要。

**跨机对照（Linux aarch64 / Rocky 10.2 / **2 vCPU** / 同一脚本、30.9 万包）**：
单核 0.350 s = 0.883 Mpps（**与 M1 Pro 单核 0.918 Mpps 基本持平** —— 单线程数字不受核数影响），
但 2 个 worker **1.00×**、4 个 worker 仅 1.11×。原因不是代码：`workers=1` 是"派发 + 处理"串行
一个线程，`workers=2` 就是 3 个线程抢 2 个核 —— 派发端在那台机器上把收益全吃掉了。
**这条对照同时提醒一个读数陷阱**：脚本的 `D = 最优档位耗时` 归因，前提是 worker 数 ≥ 核数；
在 2 核机上它会把"线程争抢"误算成"派发端"。核少的机器上应读**加速比**而不是 D 的绝对值。

**一个只有测量才暴露的缺陷（已修 + 已加常驻测试）**：分片哈希最初是 FNV-1a 后直接
`h % workers`，而 FNV 的**低位只取决于最后几个字节**，真实流量的流键尾部（目的端口 443、
协议号 6）在一批流里完全相同 → 低位恒定。实测 20000 条流在 8 个 worker 上只用到 0/4 号，
2/4 个 worker 时**全部**落在 0 号（`worker_flows=[20000,0,0,0]`）：
**输出完全正确、单测全绿、并行度为零。** 修法是取模前加一次 splitmix64 雪崩混合；
测试同时改成「按真实流量形态（变化字节在前部）的键断言均衡度上下界」——
旧测试只断言"8 个分片都被用到"，而它用的键恰好把变化放在别的字节上，所以漏掉了。

**同批修掉的另一个测试缺陷**：不变量测试原先只做「两条路互相比」，**把同一个错犯在两条路
上就看不见**（实测：删掉统计合并整行后仍然相等）。已补**绝对口径**断言：每个解码成功的包
恰好被 observe 一次（`session.packets == packets_decoded`）、会话数等于记录数、
应用识别分布总数等于记录数。

**反向注入（这次改动凭什么可信）**：① 分片改用原始五元组 → 不变量测试红；
② 去掉派发端定序 → 红；③ 删掉统计合并的一项（绝对口径补上前后）→ 红。
三条都实测过，随后还原复核全绿。

**已知限制（诚实边界）**：
- 分片模式下**每个 worker 各自持有 `--max-sessions` 额度**（总容量 = N × 额度）；一旦发生
  会话逐出或 id 耗尽，各 worker 的存活集合本就会不同，此时"与 `--workers 1` 逐字节一致"
  **不再成立**。CLI 每次都会打印 `evicted=`，下游据此判断这份输出与单线程是否可比。
- **只是离线路径**接线。在线路径（`ring-consume`）仍是单表单线程；按队列分环属 `CYS-PKT-009`。
- 测量是"页缓存热 + 独占核"的单机数字，**不能**当在线能力用（在线没有 pcap 解析开销，
  但也没有本机这种独占核）。Linux 2 vCPU 测试机上同样的扫描会更快封顶（见 §2.7 的能力边界）。

### 2.9 分层解耦与插件化方案：从评估稿升为正式方案并立项 M10（2026-10-05 第三段）

**结论先写在这里**：`docs/architecture/layered-plugin-architecture.md` 审核通过，
由 v0.1.0 评估稿升为 **v1.0.0 正式方案**，并作为**新里程碑 M10「分层解耦与插件化」**
合并进 `BACKLOG.md`（新增 §3.10，17 项；待办表 350 → **367**，里程碑 9 → 10）。

**方案的核心结论（改回去之前先读理由）**：

1. **分层解耦可行，但「功能模块全部拆成插件」不可行也不必要。** 正确形态是
   「契约下沉 · 核心单体 · 插件分级 · 第三方进程隔离」。**90% 的「分开升级」诉求由数据插件
   满足**，代码插件只该出现在少数粗粒度边界上。
2. **两条会做错的地方先纠正**：① 「核心引擎 vs 运行框架」是**库 vs 宿主**的分离，**不是插件化**
   （`traffic-engine` 早已是 `lib` + 4 `bin`，成本 S~M）；② 「特征库」必须一分为三 ——
   **提取器**（21 维定长向量，核心不可插件）/ **定义**（`attributes.json` 真源，契约 + 数据插件）/
   **扩展**（升 `FEATURE_SCHEMA_VERSION` 的插件）。
3. **形态 B（同进程静态插件）刻意不用 `dlopen`**：每包预算 14.88 Mpps 下，一次 `dlsym` 既不可
   内联也不可预测；静态注册表可做到零间接成本，已足够满足「新增能力不改核心调度」。
4. **进程外（形态 C）只用于两处**：第三方/商用引擎（许可 + 崩溃隔离，TSG F43 实证）
   与 ML 推理（ONNX Runtime 与「Rust 数据面零第三方依赖」硬冲突）。
5. **不可插件化的清单**（拆出去代价 > 收益）：`channel` 共享环解码、`flow` 流表、`session`/`tcp`、
   `reassembly`、`feature` 向量布局、`record` schema、`parser` 基础 L2–L4、`policyd` 匹配求值内核。
6. **唯一需要改核心的插件化是 DPI 检测器注册表**（`order()` 定长 `[fn;3]` + `AppId` 枚举，
   `dpi/mod.rs:57` / `types.rs:17-24`），四条不可退让：四态语义不变、检测器仍是纯函数、
   每包零分配、每条检测器自带向量。

**本次合并最关键的一条纪律：只登记「现有待办表未覆盖」的工作。** 逐一核对 TSG §8.5 预留的
24 个编号后，有 6 类**重复或已落地**（`CYS-POL-017/018/019/020`、`CYS-TIP-012`、`CYS-PLT-010`，
另有 `CYS-MLT-016` 本表已有），因此**不启用这些新号**，改为在 §3.10 顶部以「承接既有任务」挂钩。
**同一件事发两个号会把完成率算错，也会让后人重复排期。**

**顺带查出并登记的两件事**：
- `CYS-DBT-021`：上游 TSG 方案 §8.5 声称编号「均从各域现有上限顺延」，但把 `CYS-INF-035`
  分给了「可重现构建与 SBOM」，而**本表该号早已是已完成的「仓库完整性自检」** —— 一处重号，
  实际应为 `CYS-INF-036`。没去改上游正文（两份文档同时改易冲突），而是登记成可验收的任务。
- 写 §1.1 的源码计数命令时**我自己踩了 §7 第 7 条记录过的同一个坑**：`find ... -not -path '*/target/*'`
  会把 `services/telemetryd/internal/target/` 这个**名字叫 target 的 Go 包**一起排除，
  telemetryd 被算成 5 文件 / 809 行（实为 9 文件 / **1,671** 行，少算 862 行）。
  **计数排除必须锚定到具体目录，不能写裸的 `*/target/*`** —— 与「`.gitignore` 裸目录名吃源码」同形状。

**立刻可开工的第一步（不依赖 M2~M9 任何功能完成）**：`CYS-INF-037`（依赖方向门禁）、
`CYS-INF-038`（契约门禁自证 + 挂 CI）、`CYS-TRF-040`（插件清单真源）、`CYS-TRF-048`（核心库/宿主切分）、
`CYS-DBT-021`。**五项都不改任何行为**，但都是后面所有插件化工作的前置 ——
**门禁不可信，后面的插件契约就都不可信**（§4.2 的理由在这里同样成立）。

### 2.10 采集侧收口：mmap 环 vs 拷贝模式对照实测 + 丢包运行中可查（2026-10-05 第四段）

**为什么是这一段**：`CYS-PKT-008` 的验收命题（「抓包吞吐显著高于 pcap live」）从立项起就没数据
—— 此前的证据全是「能编译、能抓包」。上一批（§2.8）刚证明离线路径的上限在**派发端**，
捕获侧正是缺证据的一段：抓包本身还剩多少余量、mmap 环相对拷贝模式到底值多少，没人量过。

#### 做了什么

1. **丢包运行中可查**（`BackendStats.rx_kernel_packets` + `af_packet::stats()` 现场轮询）：
   原先 `PACKET_STATISTICS` 只在 `close()` 读一次 → **长跑期间丢包不可见**（而排障场景恰恰是
   「工具还在跑、线上已经在丢」），且被信号杀掉（`close` 没执行）这段数就永远丢了。
   现在 `stats()` 每次现场轮询并**累加**（`PACKET_STATISTICS` 是读即清零语义，赋值会抹掉历史）。
   与 macOS BPF 后端的 `stats()`（现场读 `BIOCGSTATS.bs_drop`）同构。
   CLI 另加 `--stats-every <毫秒>`，运行中周期性打印 `capture stats-now … kernel=…`。
2. **采集档位可指定且严格**：`CaptureOptions.mode` = `auto|v3|v2|recvfrom`，CLI `--capture-mode`。
   **指定即严格**：只建该档，失败就 `kRingFailed` 报错**绝不降级** —— 对照实验的全部意义在于
   「两臂真的是两条路径」，静默降级会让两臂跑同一条代码却看不出来。
   不支持档位的后端（BPF / pcap-file）**必须点名拒绝**，CLI 据此 `exit 2` 而不是警告后照跑。
3. **确定性打流工具 `cythsec-inject`**（仅 Linux，`cli/inject_main.cpp`）：自建
   Ethernet+IPv4+UDP 帧、可定速率/定帧长/定数量，**自己报 `sent/duration/pps`** ——
   测量再也不需要引入 pktgen 之类的额外依赖，分母也不会丢。
4. **对照脚本改成真能跑的形态**（`scripts/bench/live-throughput-docker.sh` +
   `scripts/bench/docker/live-throughput-inner.sh`）：四臂（libpcap live / 裸 TPACKET_V3 /
   生产后端 `--capture-mode v3` / `--capture-mode recvfrom`），veth 对做负载，
   并把包的去向**分三类记账**：socket 丢（`tp_drops`）、设备丢（`rx_dropped`）、
   softnet backlog 丢（`/proc/net/softnet_stat` 第 2 列）。

#### 顺带修掉的 4 个真 bug（共同点：从未被独立工具检验过）

| 位置 | 症状 | 根因 |
| --- | --- | --- |
| `capture/af_packet/af_packet_capture.c` | `packets=8` 却 `bytes=6.28e9` | `tp_mac` 当**块内**偏移用（应为**相对本帧头**） |
| 同上 | 一带负载就崩、pcap 缺失 | `tp_next_offset` 当块内绝对偏移（应为相对当前帧；生产实现是 `cur_off_ += next`） |
| 同上 | tshark 报 `network type 2112 unknown` | pcap 全局头 `ver_major/ver_minor` 各写成 4 字节（应各 2 字节）→ 整块后移 4 字节，`network` 字段读出来是 snaplen |
| `live-throughput-docker.sh` | 每臂 `offered=0`、脚本一处失败吞掉整轮日志 | ping 洪泛被 kill 才拿不到统计；打流进程被 kill 才拿不到自报；tshark 失败直接终止 |

第 3 条尤其值得记：**`CYS-CAP-002` 的验收标准是「产物可被 Wireshark 打开」，而它此前其实不成立**
—— 只是没人拿第三方工具开过。修完后 tshark 逐臂复核帧数与自报数一致（见下）。

#### 实测数据

**A. 容器内（Docker Desktop / M1 Pro / `ubuntu:24.04` / veth 对 / 64 B 帧 / 每轮 8 s）**

饱和（打流全速，抓包窗口内**抓到的 == 发出的**，各类丢包 0）：

| 臂 | 抓到 | 抓/发 | CPU(user+sys) | 每包 CPU |
| --- | --- | --- | --- | --- |
| L libpcap live | 11,088,260 | 1.000 | 1.46 s | 0.13 µs |
| V 裸 TPACKET_V3 | 10,126,401 | 1.000 | 0.99 s | 0.10 µs |
| **P-v3 生产后端（环）** | 10,759,233 | 1.000 | **1.27 s** | **0.12 µs** |
| **P-copy 生产后端（recvfrom）** | 7,955,841 | 1.000 | **6.30 s** | **0.79 µs** |

- **P-v3 / P-copy 端到端速率 = 1.35×**；**每包 CPU = 5.0× 更省**。
  注意两臂的 `offered` 不同（10.76 M vs 7.96 M，同一时长）：拷贝臂烧掉的 CPU 是从**打流侧**抢走的，
  所以「同样的机器、同样的时长，环能承载的包多 35%」本身就是结论，不是测量噪声。
- V/L = 0.91×：**libpcap 1.10 的 live 路径自己就走 mmap 环**（`pcap-linux.c` 用
  `TPACKET_V3` + `PACKET_MMAP`），故与裸 V3、与我们的 V3 同级。

固定速率 1.0 Mpps（两档都**零丢包**、抓到比例都是 **1.000**；下表为独立复跑的那次，
残差已归零）：

| 臂 | 抓到 | socket 丢 | CPU(user+sys) | 每包 CPU |
| --- | --- | --- | --- | --- |
| P-v3 | 6,999,936 | 0 | 0.96 s | **0.14 µs** |
| P-copy | 6,917,888 | 0 | 5.69 s | **0.82 µs** |

→ **抓到的一样多，CPU 差 5.9×**（同一实验独立复跑两次：**6.3×** 与 **5.9×**，第一次那轮
尚有 0.4 s 窗口错位导致的 5% 残差，第二次修正测量顺序后残差归零，结论不变）。
即：未饱和时两档的差别不体现在吞吐上，而体现在「同样的 CPU 预算能多抓 6 倍」；
一旦负载继续加大，这份 CPU 差就直接变成吞吐差（A 表 1.35×）。

**B. 真实网卡（Rocky Linux 10.2 aarch64 虚机 / `enp2s0` / 2 vCPU / 打流与抓包同机）**

| 配置 | 抓到 | socket 丢 | 实际打流速率（同一请求 300 kpps） |
| --- | --- | --- | --- |
| v3（环 4 MiB） | 665,283 | 0 | **165,924 pps** |
| recvfrom（`rmem_max` 默认 → 只拿到 416 KiB） | 633,926 | 27,233（4.1%） | 172,695 pps |
| recvfrom（`rmem_max` 放开到 8 MiB → 拿到 4 MiB） | 363,081 | **0** | 95,450 pps |
| v3（同上放开后复测） | 665,283 | 0 | 165,924 pps |

- **缓冲大小是一半的真相**：默认 `rmem_max=212992` 时拷贝臂只拿到 416 KiB（环是 4 MiB），
  丢 4.1%；把 `rmem_max` 放开到 8 MiB 后丢包降到 0。
  故「拷贝模式丢包」不能全算在机制头上 —— 但这也说明**用拷贝模式必须额外调内核参数**，
  而 mmap 环开箱即是 4 MiB（环大小不受 `rmem_max` 约束）。
- **放开缓冲后，代价从「丢包」变成「拖慢整机」**：同样是请求 300 kpps，抓包切到 copy 档后，
  打流侧实际只能发出 **95,450 pps**（v3 档时 165,924 pps）—— **1.74×**。
  这是本批最"系统级"的一条结论：拷贝模式的 CPU 开销不是只影响抓包，它把同一台机的
  端到端容量砍掉近一半。
- 该臂是 TX → AF_PACKET tap（本机发、本机 tap 看），**不是从线上收包**；真收包见 §2.7。
  2 vCPU 的绝对数字不可比，只用于「同机两档相对比」。

#### 结论（对外口径）

1. 「AF_PACKET 吞吐显著高于 **pcap live**」**在 Linux 上不成立**：libpcap 的 live 路径
   本身就是 mmap 环，实测 L ≈ V ≈ P-v3（CPU 均 0.1~0.2 µs/包）。这条验收命题是**设错了对照轴**。
2. 成立的命题是「**mmap 环显著优于拷贝模式（`recvfrom` 这一类短读路径）**」：
   零丢包同负载下每包 CPU 少 **5.9~6.3×**（两次独立复跑）；饱和时同机端到端速率高 **1.35×**；真实网卡上
   拷贝档把整机容量砍掉 **1.74×**。
3. **丢包可观测已做实**：运行中 `stats()` 即可读、`--stats-every` 可周期打印、
   `close()` 后仍是累加值；且**三类丢包必须分开看**（socket/设备/softnet）——
   只看 `tp_drops` 会把「丢在别处」读成「零丢包」。
4. macOS（BPF）与 Linux（AF_PACKET）的 `stats()` 语义已对齐：都是**现场轮询**。

#### 反向注入（三条，均实测）

- 去掉 `stats()` 里的 `poll_kernel_stats()` → 「close 之前可读」两条断言立刻红
  （`dropped=0 kernel=0`，而实际发了 432,604 帧）。
- 把 `+=` 改成 `=`（覆盖而非累加）→ 「close 后是累加」断言红（close 前 429,900 → close 后 2）。
- 去掉 BPF 后端的 `capture_mode` 拒绝 → 跨平台不变量「没有后端会静默接受 `--capture-mode`」红。

### 2.11 从「逐包」转到「流级」：IPFIX v1 落地（2026-10-05 第五段）

**触发这场转向的是一个量级问题**，而且是必须当场算清、否则整条路线都会错的那种：

| 口径 | 算式 | 结果 |
| --- | --- | --- |
| 单条 100G，平均 500 B | 100e9 / 8 / 500 | **25 Mpps** |
| 单条 100G，最坏 64 B 帧 | 100e9 / 8 / 64 | **148.8 Mpps**（线速下界） |
| 骨干 10 Tbps 全量 | 10e12 / 8 / 500 | **2.5 Gpps ≈ 1.25 TB/s ≈ 108 PB/天** |
| 本仓实测单机能力 | 容器饱和臂 `L 11,088,260 包 / 1.46 s`；2 vCPU 虚机真实网卡 165,924 pps；离线流水线派发端封顶 **2.33 Mpps** | 2.33 Mpps ≈ **10G 最坏帧的 16%** |
| 1:1000 采样后的 10 Tbps | 2.5 Gpps / 1000 | **2.5 Mpps → 2~10 M 条记录/s → 约 2~4 TB/天** |

结论不是「我们还不够快」，而是**逐包全量在省网是量级错误（差 3~5 个数量级）**，
再优化也到不了。运营商的做法是：**网元按采样率导出流级记录（NetFlow v9 / IPFIX / sFlow），
采集集群消费**；逐包只在少数关键点位（DPI / 取证 / 10~100G 单点）保留。
因此 `CYS-PKT-008` 那套采集能力的正确定位是**单点包级能力**，不是省网采集手段 ——
这一条已登记为 `CYS-DOC-023`，后续所有「省网」叙述都要按它核对。

**据此开工的第一件事**：让 `FlowRecord` 能被运营商既有的流级通道消费。
此前整条链的出口只有自研 JSONL，`netflow|ipfix|sflow|gnmi` 在仓库里**零命中** ——
也就是说，记录再准，也进不了任何真实采集体系。

**v1 落地内容**（`dataplane/traffic-engine/src/export/`，零第三方依赖）：

- `mod.rs`：IPFIX 编码器。报文头 16 B（version=10 / length / exportTime /
  sequenceNumber / observationDomainID）、模板集（Set ID 2）、数据集（Set ID ≥ 256）。
  IPv4 模板 id 256（11 字段：8/12 地址、7/11 端口、4 协议、1 字节数、2 包数、
  152/153 毫秒时标、148 flowId=session_id、34 samplingInterval）、IPv6 模板 id 257
  （27/28 各 16 B）。**模板分族按需携带**：只发 v4 的批不会把 v6 模板一起推出去，
  也不会因「v6 从未出现」而让 v6 模板永远停在「已发过」。
- `sink.rs`：两条通道。UDP（`--ipfix-udp host:port`，std 实现，失败计数 +
  最近错误文本）与**落盘成 pcap**（`--ipfix-pcap`，手写以太/IPv4/UDP 且**校验和真算**，
  产物可被 tshark 独立校验、可 `tcpreplay` 灌进真实采集器联调）。
- CLI：`--ipfix-udp` / `--ipfix-pcap` / `--ipfix-domain` / `--ipfix-max-msg` /
  `--ipfix-template-refresh`；统计行 `ipfix domain=… messages=… records=… seq_next=…
  datagrams=… bytes=… errors=…`，**导出失败不会被静默**（全失败时非 0 退出）。

**三条写进代码的规范细节**（写错都不会崩，只会让采集侧算错）：

1. **序列号 = 本报文之前该 Observation Domain 已发送的数据记录累计数**（RFC 7011 §3.1），
   模板记录不计入。采集器靠它发现导出丢包；写错要么误报丢包、要么把丢包读成正常。
2. **填充只允许零字节，且填充长度必须短于该 Set 里任何一条记录**（RFC 7011 §3.3.1）。
   本实现模板集天然 4 字节对齐，数据集补 0~3 字节；每条 Set 长度都是 4 的倍数。
3. **信息元素编号取自 IANA 注册表**（本次实际取表核对 13 个 IE），不凭记忆写；
   采样间隔如实填 **1（未采样）** —— 数据面还没有真采样，声明 <1 的采样率会让下游
   把采样流量当全量算（真采样登记为 `CYS-TRF-053`）。

**证据**（`bash scripts/test/test-all.sh --ipfix`，2026-10-05）：

- Rust 单测 16 项（含**逐字节手写的金标准报文**、IE 编号与 IANA 对照、序列号语义、
  模板刷新、v4/v6 分族、4 字节对齐、配置下限），`--rust` 全绿（334 lib 项）。
- `scripts/verify/check-ipfix-export.sh`：4 个样本 × **九类字段逐条比对**（tshark 解出的
  IPFIX 字段 vs 我们自己的 JSONL 记录），报文级不变量（version / length vs UDP 载荷 /
  序列号累计 / 模板可见性 / 刷新间隔），**IE 152/153 用 PDML 的线上原始 8 字节比对**
  （不经渲染串 —— 两个 tshark 版本渲染不同，见 §7 第 16 条），
  **UDP 通道收到的字节与 pcap 通道载荷逐字节相同**，
  5 项产物级反向注入（改计数值 / 改 setID / 改报文长度 / 截断 datagram / 改时标）**全部被检出**。
- tshark 侧原始证据：`Version: 10 / Length: 300 / FlowSequence: 0 / Observation Domain Id: 1`，
  模板 11 字段（8/12/7/11/4/1/2/152/153/148/34）被逐个解出并命名，数据记录
  `SrcAddr 10.0.0.1 … Octets 16 / Packets 1 / Flow Id 3 / Sampling interval 1` 与我们记录一致。

**v1 刻意不做**（避免「看起来支持了」）：RFC 5103 双方向（反转字段 = **企业位 + PEN 29305
+ 同编号**，而 `FlowRecord` 只有总量计数，硬做只能编造方向归属）与 DPI `applicationName`(96)
（变长字段与「定长无歧义」目标冲突）。两者待分方向计数 / 变长编码落地后作增量。

**紧接着做的是它的验收侧**：`CYS-TRF-054` 采集器（下一节）——没有采集侧，
「导出丢包率」这个 M11 必带口径就没地方算出来。

### 2.12 导出丢包率：一个只有采集侧能算出来的数（`CYS-TRF-054`）

上一节把记录送进了 IPFIX 通道，这一节做的是**它的验收侧**。原因在于：
导出器只能证明"我发了 N 条"，而运营商口径考核的是**"对端收到多少、丢了多少"**。
RFC 7011 恰好把这件事做成了可计算的 —— 但前提是有人真的去算：

- §3.1：`Sequence Number` = 本报文**之前**该 Observation Domain 已发送的**数据记录**累计数
  （模板记录不计入）。于是 `本报文序号 − 上次期望序号` = **中间丢掉的记录条数**。
- §11.6：采集进程 **MUST** 跟踪序号发现丢失/插入，并 SHOULD 提供越序日志。

也就是说，"导出丢包率"不是我们自研的指标，而是**协议里已经留好的观测点**；
不做采集器，这个数就只能靠导出侧自说自话。

**落地内容**（`src/ipfix/collector.rs` + `src/bin/ipfix_collect.rs`）：

| 环节 | 做法 | 依据 |
| --- | --- | --- |
| 序列号记账 | 只在**前进方向**记缺口；差值 ≥ 2^31 视为乱序/重复/重启，**不重置基线** | §3.1 / §11.6（点名"见大序号就重置"会被注入蒙蔽） |
| 首报文 | **不算丢包**（没有基线就没有缺口）——"采集器启动前丢了什么"不可知，属"采集覆盖率"口径 | — |
| 模板生存期 | 按**观测到的重传间隔 × 3**（可 `--template-timeout` 覆盖；未观测到时 600 s），到期即丢弃 | §8.4 |
| 模板撤回 | UDP 上**忽略并计数**（本仓只有 UDP 路径） | §8.4（UDP 下 MUST NOT 发、MUST 忽略） |
| 同号不同定义 | 保留旧模板 + 计数告警，**不用新定义解释后续数据** | §8.1（此时"已无法无歧义解释"） |
| 未知 IE | **按长度跳过**（不是删掉！）——删掉会让后面所有字段偏移前移 | 见 §7 第 18 条 |
| 缩减长度编码 | 按实际字节数读整数（unsigned64 可以是 1~8 字节） | §6.2 |
| 去重 | 有界窗口（默认 4096 条），键 = (flowId, 起止时标, 计数) | 窗口大小如实暴露，口径可解释 |
| 输入 | `--pcap`（时间取**抓包时间戳** → 可复现）与 `--udp`（在线） | — |

**证据**（`bash scripts/verify/check-ipfix-collect.sh`，已挂进 `--ipfix`）：

- **完整回路逐字段相符**：导出 9 条 → 采集还原 9 条，五元组/包数/字节数/flowId/起止毫秒
  **9/9 全部一致**；
- **导出丢包率可证伪**：从 pcap 里删掉**中间**那个 datagram（5 → 4 个，丢 2 条记录），
  采集器必须报 `gaps=1 lost_records=2`，且 `loss_ppm=222222` 与独立手算
  `2/(7+2)` **逐位一致**；删首尾测不出缺口（首部无基线、尾部无后续），故刻意删中间；
- **反向断言**：无注入时必须 `gaps=0 lost_records=0 loss_ppm=0` ——
  否则"无论收到什么都报缺口"会让上面那条正向断言**恒真通过**；
- **判定自身 6 项反向注入**：缺口条数/缺口次数/丢包率改坏、把"没有丢包"伪造成有缺口、
  分母算错（按 `records` 而非 `records+lost`）逐个被判红，外加 1 项"正确的一对必须过"。

**两机复验（2026-10-05）**：macOS（M1 Pro，tshark 4.6.9）与 Rocky 10.2 aarch64
测试机（2 vCPU，tshark 4.4.2 / python 3.12.13）上 `--ipfix` 全绿：回路均 9/9 相符、
`gaps=1 lost_records=2 loss_ppm=222222` 均与手算一致、6/6 注入均被判红；
`--live` 两机均 **15 项断言**通过（含新增的合成非首片分片完整判定链自证）；`--rust` 两机均 359 项。

**口径边界（不要在报告里抹平）**：

1. `loss_ppm` 是**导出丢包率**，不是"网络丢包率"：它同时包含网络丢失、采集侧丢弃与
   导出侧自己丢的记录（§10.2.2 要求导出侧丢记录时必须让序列号体现出来）；
2. **在线模式本版无法设置 `SO_RCVBUF`** —— `std::net::UdpSocket` 没有该接口，而本仓不做
   第三方依赖（socket2/libc 都不引）。默认 rmem 在突发下会溢出，**内核丢的正是我们自己的包**，
   于是这些丢弃会以缺口形式混进 `loss_ppm`。结论：本版该指标只在**低突发**（离线重放/单机回环）
   下口径干净；线速现场必须先按 `CYS-PKT-032` 那批内核侧工作解决；
3. 采集器还原不出 TCP 状态与 DPI 结论（IPFIX v1 模板里没有），故如实写
   `tcp.state = null`、`app.outcome = "not_inspected"`、`risk_score = null` —— 门禁专门校验这一条，
   免得把"没采集到"伪装成"采集到了但值为空"；
4. IE 152/153 是**毫秒**，故回路比对按毫秒粒度：亚毫秒信息在导出那一刻就不存在了。

**两条用法约束**（踩过：单独选会被脚本直接拒绝并 `exit 2`）：

- `--parity` 与 `--e2e` **必须与 `--cpp --rust` 同时选** —— 它们校验的对象是
  编译出来的两端产物/进程，缺一侧就无法成立。脚本拒绝是刻意的：
  *静默跳过会让人以为验过了*。
- 前端**类型检查不在这里**，在 `lint-all.sh` 里（静态检查不依赖运行时）。
  分开的理由：`test-all.sh` 需要真实构建产物，`lint-all.sh` 只看源码文本。
- **`scripts/verify/bench-pipeline.sh` 不是门禁**（不在任何分组里，也不会自动跑）：
  它量的是"加 worker 有没有用、上限在哪"，绝对吞吐机器相关，**刻意不做阈值判定**。
  它的**正确性**部分已由 `--rust` 里的单测常驻把关（1/2/3/4/8 个 worker 输出逐字节一致、
  分片均衡度上下界、两个方向必须同分片）。用法：`bash scripts/verify/bench-pipeline.sh [包数] [轮数]`
  （先 `cargo build --release --offline`），结论见 §2.8。
- **`scripts/bench/live-throughput-docker.sh` 也不是门禁**（不在任何分组里）：它量的是
  「mmap 环 vs 拷贝模式」的对照，绝对数字随机器/容器配额变化，**刻意不做阈值判定**（脚本末尾
  明写）。它的**正确性**部分已由常驻测试把关：Linux 侧 `test_capture_modes`（档位强制 +
  「小环+洪泛 ⇒ 丢包必须在 `close()` 之前可读」+「close 后是累加不是覆盖」），
  且三条都做过反向注入（见 §2.10）。用法：
  `bash scripts/bench/live-throughput-docker.sh [时长秒] [帧长] [速率pps]`（速率 0 = 全速），
  结论见 §2.10。
- `--bench` **刻意不在"全部"里**（`ALL` 集合不含它）：它的回归下限标定在特定机器上
  （Apple M1 Pro / macOS / 1M 条规模），换机器、换核数、开省电模式都会变。
  进默认集合只会变成"随机红的门禁"，而随机红等于没有门禁。换机器后先
  `--report-only` 看真实数字再重标定。

**lint 九项明细**：`[cpp] clang-format` · `[rust] cargo fmt` · `[go] gofmt` ·
`[codegen] 属性字典生成物一致性` · `[codegen] 通道 ABI 双端契约一致性` ·
`[version] 版本单一真源一致性`（这一项跑两步：真实校验 + 检查器自证）·
`[repo] 有没有源码被 .gitignore 静默忽略` ·
`[node] 前端类型检查（vue-tsc / tsc --noEmit）` · `[node] eslint`。

**`test-all.sh` 现在会先自动生成向量**（`gen_datasets`）。
理由：`datasets/**/*.pcap` 与 `*.json` 都在 `.gitignore` 里（字节级可复现，
不该占 diff），而 Rust 刻意用 `include_bytes!` 把向量**编进二进制**
（路径错 = 编译失败，而不是运行时静默什么都不测）——
所以全新克隆里缺文件是**硬失败**，必须有人补齐。

### 4.1 三方互证方法论（本项目最重要的方法论）

```
生成器（知道放了什么，自算期望值）
      ↓ 同一份 expected.json
Rust 实现（读期望值断言）
      ↕ 独立比对
tshark（第三方独立实现）
```

**为什么必须有第三方**：一致性本身证明不了正确性。只要生成器和实现犯**同一个**
理解错误（比如都把 GREASE 算进 JA3、都把握手长度当 2 字节），两边依然会完美一致。
tshark 是唯一能发现「一致地错」的手段。

**已知例外必须显式标注**，不能默认通过。目前共 3 条：

| 例外 | 原因 |
| --- | --- |
| `tls-ech-no-outer-sni` | tshark 4.6.7 的 ECH 解析器认不出手工构造的 ECH 体，会连整包 JA3 一起抑制 |
| `overlap-conflict` | 重叠仲裁策略与 tshark 不同且不可配置，两边期望值必然不同 |
| `memory-cap` | tshark 没有内存上限，会把被本实现丢弃的段也算进重组结果 |

三条都在 `expected.json` 里标 `tshark.verified=false` + 写明原因，
**并有测试守门**（`ech_vector_is_marked_as_not_tshark_verified`、
`known_exceptions_are_explicitly_marked`）防止被悄悄改回 `true`。

### 4.2 改动后必须做的反向注入验证

「检查通过」与「检查根本没跑」的输出都是绿色。因此**新增或修改门禁后**，
必须注入一个必然违规的输入确认它会报错，再恢复现场并做字节级比对。

本批三次注入的实际结果（都写进了提交信息）：

| 注入 | 结果 |
| --- | --- |
| 改坏 `expected.json` 的 sha256/len/memory_drops | ✓ 两道门禁双双报错（`exit=1`） |
| FIN 序号写成 `seq`（漏算载荷长度） | ✓ 2 项测试失败 |
| 把 `feed` 里「先数据后 FIN」对调 | ✗ **76 项测试全绿** |

第三次是**有价值的失败**：它证明了该顺序对最终状态实际无影响
（`on_fin` 只记序号，与插入互不干扰），于是把源码里那句
「顺序**必须**是先数据后 FIN」的夸大注释改成了真实约束
（真正敏感的是 FIN 的**序号**）。教训：注释里写的因果关系也要被验证。

## 5. 项目约定（必须延续）

1. **C++ 新增文件必须跑 `clang-format -i`**
   工具在 `/Library/Developer/CommandLineTools/usr/bin/clang-format`（**不在 PATH**）。
   历史事故：29/30 文件不合规却因检测不到工具而被静默跳过，
   本地绿灯、CI 必红。本轮又复发一次（新文件未格式化），已全仓修净。
   → **建议把 `clang-format -i` 变成保存钩子或 pre-commit**。

2. **shell 中变量引用一律用 `${VAR}` 花括号形式**
   macOS 自带 `bash 3.2.57` 会把紧跟 `$VAR` 后的多字节字符**并入变量名**，
   在 `set -u` 下直接 `unbound variable` 中断。历史 6 处事故 —— **本批又踩了第 6 次**
   （新写的 `check-flow-bench.sh` 里 `$ROUNDS）` 直接把右括号并进变量名）。
   新脚本一律先按 `\$([A-Za-z_][A-Za-z0-9_]*)` → `${...}` 批量加花括号，再 `bash -n` 验证。

3. **注释里声称「有脚本会拦下」的，该脚本必须真实存在、在版本控制里、并挂在门禁上**（三条缺一条都等于没有）
   历史事故：4 处注释这么写，而那个脚本**并不存在**。

4. **真源单一**：`configs/registry/*.json` 是唯一真源。
   四语言侧只允许**引用生成物**（`attributes_gen` / `abi_gen`），
   禁止手写 `"ATTR_..."` 之类字面量。

   **本批给出这条约定的三个真实反例**（同一天、同一条 ignore 规则家族）：
   `scripts/release/check-version.sh` 正确且存在，却 ① 没有任何门禁调用它，
   ② 它所在的 `scripts/release/` 被 `.gitignore` 的裸 `release/` 规则整个忽略、
   **从未入库**；③ 同一条规则家族还吞掉了 `scripts/build/build-all.sh`（四端构建入口）
   与 `services/telemetryd/internal/target/`（telemetryd 直接 import 的 Go 包，
   全新克隆里 `go build ./...` 直接失败）。
   「有检查器」和「检查器会跑」和「检查器在仓库里」是三件事，任何一件缺失，
   绿色的门禁都与「没检查」无法区分。现由 `[repo]` 那道 lint 专门守这一类（见 §7.7）。

5. **未识别 ≠ 识别为无**：SNI 为 `None` 时**不产出** `ATTR_TLS_SNI`，
   而不是产出一个空串属性。空串在下游会被当成「确实没有」，语义相反。

6. **测试向量必须编进二进制**，不许运行时读文件。运行读文件的话，
   路径写错或工作目录不对时测试会「安静地什么都测不到」——输出全绿，
   实际一条断言都没跑。这是本项目反复踩过的假绿灯。

7. **期望值手写，不许「跑一遍实现记下来」**。后者等于让被测实现给自己的
   答案打分，两边一起错的时候看不出来。

8. **性能门禁的阈值必须分成"需求目标"与"回归下限"两套**（见 §2.5）。
   需求目标由工作量需求推导（公式写在源码注释里），回归下限才允许是"本机实测"。
   把实测值当验收标准，等于用实现给自己打分；把需求目标当退出码，则会在差距
   还没排期时让门禁天天红。两者都不能省。

9. **报告与判定分离，且判定逻辑只有一处**。同一个判据被复制到"打印"和"退出码"
   两处，迟早会分叉成"表格说达标、脚本说失败"。基准的 `--report-only` 与
   `--require-targets` 就是这条约定的产物。

10. **量出来的问题，要么修，要么带数字进 §6**。基准首轮抓出三处，两批共修掉两处；
    剩下的一处（10G 吞吐）带着实测数字写进清单 —— 语义/架构级变更需要显式决策，
    不能藏在性能提交里。

11. **性能改造必须给出三样东西，缺一不可**：① 同机、同参数、背靠背的**前后对比**
    （不是各跑一次隔几天比）；② 复杂度的**可测证据**（本批是 `stats().evict_candidates`：
    链表策略必须恒为 0，扫描策略必须是"每片容量 × 逐出次数"，谁把 O(1) 改回 O(容量)
    测试立刻红）；③ 被否掉的方案也要带数字（采样 LRU 被 58.4% vs 99.9% 的热点命中率
    否掉，写进 `EvictPolicy` 的注释）。只有挂钟时间的前后对比会被负载漂移骗过去。

1. **批量删除保护会拦 `npm ci`，且报错信息误导**

   - `test_node()` 先看 `web/console/node_modules/.bin/vitest`：在位就直接 `npm test`，

7. **`.gitignore` 里的裸目录名会吃掉同名的源码目录**（本批最贵的一课，一次踩出三处）。
   `build/` / `target/` / `release/` 这类**不带前导斜杠**的目录名，按 gitignore 规则匹配
   **任意层级**的同名目录，于是同名源码目录被整体忽略 —— 文件在磁盘上、执行权限正常、
   本地跑得通，但不在版本控制里，**全新克隆里没有它**，`git status` 也永远不提示：

   | 被吃掉的东西 | 后果 |
   | --- | --- |
   | `scripts/release/`（`check-version.sh`） | 版本自检脚本从未入库，README 与交接文档却在引用 |
   | `scripts/build/`（`build-all.sh`） | 四端统一构建入口从未入库 |
   | `services/telemetryd/internal/target/`（Go 包，4 文件） | telemetryd **直接 import** 它 → 全新克隆 `go build ./...` 直接失败 |

   规则已全部锚定到根（`/build/`、`/cmake-build-*/`、`/target/`、`/out/`、`/dist/`、`/release/`），
   三处文件已入库，并新增门禁 `scripts/verify/check-ignored-sources.sh`（`lint-all.sh`
   的 `[repo]` 一项）在**版本控制的事实**上守这一类回归 —— 它扫描
   `git ls-files --others --ignored --exclude-standard` 里的源码/脚本类文件，
   命中即报错并打印是哪条 ignore 规则吃掉了它。

   某个自己刚写的文件时，先怀疑 ignore 规则而不是编辑器。
   **更要紧的是「怎么发现的」**：三处都不是读代码看出来的，而是**在全新克隆里跑门禁**
   才暴露的（`check-version.sh` 报 `scripts/build/build-all.sh` 不存在、Go 编译报缺包）。
   本地全绿 ≠ 克隆能构建；发布/交接前请真的 clone 一次再跑。

8. **`core.autocrlf=input` 会把入库的二进制向量改掉行尾**（与第 7 条同属「磁盘上有 ≠ 版本控制里是那份」，
   但更难发现，因为这次文件**在**版本控制里，只是内容被悄悄改了）。
   本机 `core.autocrlf=input`（全局也是），`git add` 会把 HTTP 向量载荷里的 `\r\n`
   归一成 `\n` —— 而 `http.rs` 正是用 `\r\n\r\n` 判头部结束。实测表现：
   `git add datasets/dpi/payloads/http-response-200.bin` 打印
   `CRLF will be replaced by LF`，索引 blob 的 CRLF 计数变成 **0**，磁盘上仍是 **5**。
   修复：`.gitattributes` 声明 `datasets/**/*.bin -text`（向量载荷是不透明字节）+
   `git add --renormalize datasets/dpi/payloads/`。

   **两个反直觉点，别绕过去**：
   - **`git diff` 看不见这种损坏**。它比对的是"过了 clean 过滤之后"的内容，而行尾归一
     恰恰发生在过滤这一步，于是"索引 LF / 磁盘 CRLF"在它眼里毫无差别（实测 `git diff --quiet`
     报干净）。必须逐文件比对**未经过滤**的字节：`git ls-files -s` 的 blob 哈希 vs
     `git hash-object --no-filters`。
   - **`.gitattributes` 会被缓存在索引里**。把文件删掉后 `git check-attr` 仍报 `text: unset`，
     于是"去掉属性验证会不会复发"这种实验会得出**假的结论**（我第一轮就被它骗过一次）。
     要让改动生效需重写索引（如 `git rm --cached .gitattributes` 后再看 `check-attr`）。

   守门：`scripts/verify/check-dpi-vectors.sh` 的正常执行会先跑一遍**自证**
   （在临时仓库里真的制造一次行尾归一 → 断言能判红；加 `-text` → 断言判绿），
   再逐文件比对 32 个入库向量与生成物字节；`--self-test` 可单独跑。
   挂在 `test-all.sh --dpi`（默认全量门禁含该项）上。

9. **跨机同步代码：`tar --exclude` 会静默吃掉源码，`git archive` 才是对的**（2026-10-05）
   macOS 自带的 `tar` 是 bsdtar：`--exclude=./target` / `--exclude=./build` 匹配的是
   **任意层级**的同名目录，实测静默丢掉了 `scripts/build/build-all.sh` 与
   `services/telemetryd/internal/target/*.go`（共 5 个文件）—— 正是第 7 条那类
   「磁盘上有 ≠ 版本控制里有」，而且这次连目标机上都是缺的。正确姿势：

   ```bash
   git archive --format=tar HEAD | ssh <host> 'mkdir -p <dst> && tar -xf - -C <dst> --no-same-owner'
   COPYFILE_DISABLE=1 tar -cf - .git | ssh <host> 'tar -xf - -C <dst> --no-same-owner'
   ```

   另外三个坑：① 以 root 解包会保留 macOS 的 uid → git 报「可疑的所有权」，需
   `chown -R root:root`（或 `safe.directory`）；② 不加 `COPYFILE_DISABLE=1` 会带进
   AppleDouble `._*`，`.git/objects/pack/._*.idx` 会让 git 报 `index file ... is too small`；
   ③ bsdtar 的 `LIBARCHIVE.xattr.com.apple.provenance` 警告是噪声（`--no-xattrs` 或丢给 `/dev/null`）。
   **自证**：同步后目标机上 `git status --short` 必须 **0 行**。
   相关：**干净克隆里直接 `cargo test` 也会失败** —— `datasets/**/*.pcap|json` 是被
   `.gitignore` 忽略的生成物，而测试用 `include_bytes!/include_str!` 引用它们，
   必须走 `scripts/test/test-all.sh --rust`（会先生成向量）。

10. **测试里写死的「平台常识」换机器就是假红**（2026-10-05 一次抓到 3 处，详见 §2.7）
   - `0xFFFF` 当「未知链路类型」：Linux 上是具名的 `ARPHRD_VOID`（`0xFFFE` = `ARPHRD_NONE`）。
   - `kNoSuchIface` 用 32 字符：`IF_NAMESIZE`=16 → `open()` 先报「接口名过长」而非「不存在」。
   - 串行档断言「效率 < 下限 0.25」：2 核机器表达不出抢锁（实测 0.33）。
   **共同的修法**：取值/阈值不要凭"在 macOS/本机上看起来合理"来定 —— 要么改成相对量
   （比值、与核数无关的兜底），要么显式限定适用条件（`ap >= 4` 才断言），
   并把期望值由常量算出而不是抄一份字面量。**假红与假绿同样有害**：假红会让人干脆关掉门禁。

11. **哈希取模分片：低位是"坑位"，FNV 的低位只由最后几个字节决定**（2026-10-05，见 §2.8）
   流键尾部（目的端口 443、协议号 6）在一批流量里完全相同 → `fnv(...) % workers` 的低位恒定，
   20000 条流全挤到一个 worker，**输出完全正确、单测全绿、并行度为零**。
   修法：取模前做一次雪崩混合（splitmix64 收尾）；测试必须按**真实流量的字节布局**
   （变化在前部）断言**均衡度上下界**，只断言"每个分片都被用到过"会漏掉它。
   一般化：任何"把结构化键映射到 N 个桶"的地方（分片、分区、负载均衡）都要用
   *先混合再取模*，并且用真实分布的键测均衡，而不是用人为把变化放在中间字节的键。

12. **`ssh <host> '命令'` 是登录非交互 shell，PATH 里没有 `~/.cargo/bin`**（2026-10-05）
   在测试机上 `ssh cythsec-dev-ho 'bash scripts/test/test-all.sh --rust'` 直接报
   **`✗ 工具链缺失: cargo`** —— 而同一台机上交互登录 `cargo --version` 是好的
   （rustup 把 PATH 写进了 `~/.bashrc`/`~/.profile`，非交互 shell 不读它们）。
   一律写成 `ssh <host> 'export PATH="$HOME/.cargo/bin:$PATH"; cd … && …'`。
   **注意这里没有"改门禁让它别报错"的余地**：预检是对的（非交互环境里的确没有 cargo），
   要修的是调用姿势。同类坑：任何"我本机命令行能跑"的脚本都可能栽在非交互环境上。

13. **装在引号串里的脚本，外层 `bash -n` 查不出语法错**（2026-10-05，白等两次容器启动）
   容器内脚本原先以 `docker run … bash -c '…'` 的形式嵌在外层单引号串里。写错一行后：
   外层 `bash -n` **照样通过**（内层的引号与外层配平了），错误要等容器起来、装完依赖、
   编译到一半才炸 —— 每轮白等 4 分钟；而内层里再出现一个单引号，更会直接截断外层字符串
   （症状是容器内莫名语法错）。
   修法：**内层脚本独立成文件**（`scripts/bench/docker/live-throughput-inner.sh`），
   外层先用 `bash -n` 检查它，再 `docker run -i … bash -s -- <参数> < inner.sh` 喂进去。
   一般化：任何"把脚本当字符串传给别人执行"的地方，都要让**被传的那份能被直接 `-n`**。

14. **`SO_RCVBUF` 会被内核按 `net.core.rmem_max` 静默削顶，`PACKET_RX_RING` 不会**（2026-10-05）
   同一份代码里：mmap 环请求 4 MiB 得到 4 MiB；`recvfrom` 路径请求 4 MiB 在
   Rocky 10.2 上**只拿到 416 KiB**（`rmem_max=212992`），于是拷贝臂丢 4.1% 的包，
   而只看代码会以为两档缓冲同量级、把丢包全算到"机制"头上。
   修法：**设置后必须 `getsockopt` 回读**，被削顶时写进 `fallback_reason_` 让 CLI 报出来。
   一般化：凡"请求一个内核资源上限"的地方（缓冲区、环、队列深度、`max_backlog`），
   都要回读实际值 —— 内核不报错不代表给了你要的。

15. **`tp_mac` / `tp_next_offset` 是相对「本帧头」的偏移，不是相对块首**（2026-10-05）
   `capture/af_packet/af_packet_capture.c` 把两者都当块内偏移用：数据指针落在块内随机位置
   （实测 `packets=8` 却 `bytes=6.28e9`），一跳下一帧就越界崩。
   口径以 `<linux/if_packet.h>` + **本仓生产实现**（`af_packet.cpp` 的 `cur_off_ += next`）为准，
   别按直觉推。同类：V3 的 `num_pkts`（不是 `num_pkts_active`）、`offset_to_first_pkt`
   （不是 `offset_to_first_hp`）—— 字段名写错在 C 里是**编译期**就能抓到的，前提是真的编译过。

16. **tshark 解 IPFIX 的字段名与直觉不同，且时间藏在子节点里**（2026-10-05）
   Wireshark 用 `cflow.*` 解析 IPFIX/NetFlow，名字不能凭 IE 名猜：
   `flowId`(148) 是 **`cflow.flow_id`**（不是 `cflow.flowid`）；起止时间是
   **`cflow.abstimestart` / `cflow.abstimeend`，且嵌在 `cflow.timedelta_tree` 子节点里**
   （`-T fields` 下取不到）；只带**一个**模板的模板集，其 `cflow.template_id` 藏在
   `Template (Id = …, Count = …)` 子节点下。结论：**按字段名递归收集**，别写死键路径 ——
   写死的键一换样本就炸。
   **更要紧的一条：JSON 里渲染好的时间是"显示偏好"，不是协议事实** —— 同一份产物，
   macOS tshark 4.6.9 给 `2023-11-14T22:13:30.016000000Z`，Rocky 4.4.2 给
   `Nov 15, 2023 06:13:30`（本地化），解析渲染串会在换机器时直接崩。
   改用 `-T pdml` 的 `value=`：那是该 IE 的**线上原始字节**（`0000018bcfe58f20`），
   与 locale / 版本 / 显示偏好全无关。**第三方核验要取原始值，不要取它给你看的字符串。**

17. **bash 3.2（macOS）：`$var` 紧跟全角字符会被当成变量名的一部分**（2026-10-05）
   形如 `echo "…（模板刷新 $refresh）"` 报 `refresh）: unbound variable` ——
   bash 3.2 会把紧跟 `$var` 的多字节字符吃进变量名。中文输出里**一律写 `${var}`**。
   同源坑：`set -u` 下展开**空数组** `"${arr[@]}"` 也报 unbound variable，
   惯用法是 `${arr[@]+"${arr[@]}"}`（本仓 `check-ipfix-export.sh` 里两处都踩过）。

18. **"跳过不认识的字段"必须按长度跳过，不能把它从字段表里删掉**（2026-10-05）
   解析 IPFIX 数据集时，未登记的 IE 若直接从字段列表里剔除，后面所有字段的偏移会整体前移，
   而前移后读出来的**仍是合法字节** —— 本批就踩到了：octets 读成了 `0xAABBCC0000000000`
   （前 3 字节是那个未知 IE 的内容），**数值离谱但不会崩、不会报错**，只有手写期望值的
   单测能抓住它。修法：偏移**先推进再决定解不解**（`ipfix/collector.rs`）。一般化：
   凡是"TLV 里跳过不认识的类型"的地方，长度永远要计入，语义才可以忽略。

19. **`std::net::UdpSocket` 没有任何设置 `SO_RCVBUF` 的接口**（2026-10-05）
   于是"把采集侧收包缓冲放大"这件事在**零第三方依赖**的前提下做不到
   （socket2/libc 都不引）。这不是可以含糊过去的细节：默认 `rmem_default` 在高突发下溢出，
   **内核丢的是采集器自己的包**，而这些丢失会以"序列号缺口"形式出现，
   把采集侧的问题算成导出丢包率。故：该指标只在低突发下口径干净，
   并在 §6 与 `--udp` 的帮助文本里都写明。

20. **"两个独立实现判定不一致"不等于"有一方错了"**（2026-10-05）
   `--live` 的 D 项断言比的是"我们对哪些帧解不出五元组"与"tshark 判定的非 IP 帧数"。
   两次假红，病根相同：**判据里藏了依赖现场流量的隐藏变量**（第一次是 802.3/LLC 帧没有
   EtherType，第二次是**非首片分片**——tshark 仍写 `eth:ethertype:ip`，而我们按设计拒绝，
   因为端口在首片里）。表现都是"偶尔红"，靠真实流量去等它复现等于靠运气。
   一般化做法：把"按设计拒绝"的类别**逐条枚举进裁判口径**，再断言相等；
   并把每条类别做成**合成语料的确定性自证**（灌环跑完整判定链，不依赖现场流量）。
   附带一条更硬的教训：**"两个数相等"不能单独当自证** —— 夹具写错时会"两边一起瞎"，
   等式照样成立；至少有一个数必须来自与被测对象无关的独立期望值（这次就是那条独立期望值
   抓到了我写歪的 IPv4 首部）。

## 10. 一句话交给下一棒

「从报文到可存储记录」这一段**已经通了**：`Packet → FlowTable → Session →
FeatureExtractor → FlowRecord`，有离线路径 `cythsec-analyze -r x.pcap -o flows.jsonl`，
有带反向注入的 tshark 门禁（`--flows`），现在**还有了数字**（`--bench`）：
1M 条流可容纳（0.97KB/条）、插入达标（2.06 Mops/s）、稳态无内存增长成立；
基准量出的三处问题**已修两处**：`expire()` 的 O(n) 临时数组、`evict_lru` 的 O(每分片容量)
（后者改成分片内双向链表，仍是精确 LRU、逐出 O(1)：52µs → 0.34µs@每片8192，并给出
"每次逐出考察 0 个候选"的可测断言）；剩下的是稳态查表只有 10G 需求的 34~38%。

下一棒最有价值的三件事，按性价比排序：

1. **稳态吞吐与 10G 的差距**：update 5.6 / query-hit 5.0 / query-miss 13.8 Mops/s vs 需求
   14.88 Mpps。先做一个便宜实验（每核一个独立流表实例，证明近线性扩展），再决定是走
   "多实例分核"还是"把 432B 条目拆成热/冷两段"。别在没有实验数据的情况下直接重构流表。
   （本批已交出一次可比对的教训：O(1) LRU 让插入快一倍、逐出快 100 倍，但命中路径多一次
   间接寻址就吃掉 35% —— 结构改动必须前后同机量。）
3. **特征定义单一来源**（`CYS-TRF-028`）+ **控制平面落地侧**（`CYS-POL-007/008/005`）：
