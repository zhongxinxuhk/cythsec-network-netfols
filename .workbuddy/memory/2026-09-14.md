### 测试捕获的真实缺陷（已修复）

`src/utils/format.ts` 的 `fmtBytes()` 对 `n < 1024` 走了通用小数分支，`fmtBytes(1)` 输出 `1.00 B`。
字节是离散计数，小数位无有效信息。已修：`i === 0` 时固定取整。并补边界用例锁定：
`0`/负数→`0 B`、`1023`→`1023 B`、`1024`→`1.00 KB`、`1024**5`→`1024 TB`（超 TB 不再进位）。

> 这个缺陷正在于「先写测试」的价值：读代码时不会觉得有问题，写了边界断言才暴露。

### 关键设计决策（编码时定型）

- **部署模式把能力可用性从文档约定提升为代码约束**：`SubActionAvailable(原语, 模式)` 是唯一判定入口。
  旁路（SPAN/TAP）物理上不在报文路径，`drop_stream`/`drop_current_packet`/`throttle_*` 返回 false。
  不做成硬约束就一定会出现「规则命中但流量照走」的静默失效。
- **诊断严重度按「是否启用」分级**：启用规则用了当前模式不可用的原语 → **阻塞错误、拒绝装载**；
  停用规则 → **提示警告、允许装载**。前者会让设备静默失去防护，必须拦。
- **`deploy_mode` 默认 `bypass`**：这是唯一「不会让人误以为已生效」的默认值。
- **白名单先于拒绝**（与论文 §4.1.2 相反）：安全设备最贵的故障是误封。
- **装载失败即致命**：规则表是安全策略，静默以空表启动＝全部阻断规则失效。
- `Registry.Install` 保持「全量成功或全量不生效」原子性，拒绝时保留旧快照。

## 第三批：门禁可信度修复 + 通道 ABI 三层防线补全

### 核心主题：门禁自身不可信

| 门禁 | 假象 | 真相 |
| --- | --- | --- |
| `lint-all.sh` C++ 格式段 | 「通过」 | `command -v clang-format` 在 macOS 上失败（工具在 `/Library/Developer/CommandLineTools/usr/bin/`，不在 PATH）→ **整个 C++ lint 从未执行过**。补测发现 29/30 文件不通过 |
| `abi_gen.h` 的 35 条 `static_assert` | 「有编译期防线」 | header-only 且全仓**零翻译单元 include 它** → 断言从未被求值 |
| `test-all.sh` 的 C++ 栈 | 「测试通过」 | 只跑 `ctest` 不重建 → 拿上次产物验收当前源码；`ctest` 报 `Not Run` 时仍算通过 |

处置原则（本轮定型，可复用）：**「工具找不到」必须计为失败，不得静默跳过**；
**「上一次的绿」不是绿**，验收前必须先构建。

### 修出的真实缺陷（9 项）

1. **master 主干 Rust 无法编译**（最严重）：`region.rs` 引用 `AttachError::SlotCountMismatch/SlotSizeMismatch`，
   而真源 `channel-abi.json` 中这两条诊断**已被误删**、生成枚举无对应变体 → `cargo build` 2×E0599。
   核实依据：`channel/tests.rs` 明确断言这两个码 + `attach_expect` 语义需要它们 → 判为误删，在真源恢复。
2. **诊断可达性检测器成片误报**：`_is_constructed` 只认 `diag::ChanX` 形态，不认识 `AttachError::X`
   枚举变体构造 → 9 条实际已实现的诊断被报为死诊断。**真信号被误报淹没 = 检测器失效**。
   修法：登记 `impl_ident` 例外字段（唯一不遵循命名规律的 `chan.io_error` → `Io`），并扩展判定口径。
3. **`check-channel-abi.sh` 被 4 处注释引用却不存在** → 补齐并挂入 `lint-all.sh`。
4. **`attach_expect` 校验顺序违反自身声明**：把「配置期望 vs 区域值」比对放在 `validate` 根基校验**之前**，
   导致未初始化区域误报 `slot_count_mismatch` 而非 `chan.uninitialized`。移到 `validate` 之后，并加测试锁定顺序。
5. **`attributes.gen.ts` 生成物编译不过**：三个 `*_DESC` 映射的键误用 PascalCase 派生名，
   而其类型是 `Record<AttrScope, string>`（键取自枚举**值**联合，小写）→ TS2561 ×6。
   前端 `typecheck`/`build` 双红。修法：DESC 表键改用规范标识。
6. **前端版本号注入链路从未生效**（`CYS-INF-020`）：`vitest.config.ts` 路径写三级上溯
   （解析到仓库**外**），且 `catch` 静默回落 `'dev'` —— 版本号「看起来有值」，实际从未来自 `VERSION`。
   根因是**同一逻辑两份副本、只改了上游一处**。修法：抽出 `web/console/version-source.ts` 单一真源，
   去掉静默兜底（读不到直接构建失败）。
7. **`test-all.sh` Go 栈漏 `pkg`**（上批已记）与本批 C++ 栈「用旧产物验收」。
8. **`@types/node` 缺失**：`tsconfig.node.json` 检查构建配置时报 `process`/`__dirname` 未定义 →
   安装 `@types/node@^22`，并把「构建配置类型检查」纳入门禁（原只查 `src/tests`）。
9. **`cargo fmt` 5 文件未格式化**（既有漂移）。

### 注入验证抓到的两个真实缺口（本批最高价值）

1. **诊断文案含游离空格**：注入「`desc.data_off` 误用区域相对偏移」后诊断如期报错，

   已全仓扫描同类痕迹（扩展扫描到 `.cpp/.h/.rs/.py/.sh`）并修净。
2. **注入逃逸——门禁有洞**：注入「生产端 `published` 双计」后 **19 项断言全部通过**。

   而那正是运维排障唯一能看的字段。

> 结论沉淀：**「一次逃逸的注入，信息量远大于十次通过的注入」**。

- **第 5 要素「核对共同状态，而非只核对各方自述」**：多组件系统里各方自述可以**一致地错**。
- **新模式 H（多组件只核对自述）/ 模式 I（汇总数字写死）/ 模式 J（同格式复用同名键致抓取取错值）**；
  注入模板新增「多进程共同状态」一节，附「逃逸时应判为门禁缺口而非注入无效」的判读表。
