## 2026-10-05 采集侧收口：mmap 环 vs 拷贝模式对照实测（`CYS-PKT-008` → ✅、`CYS-CAP-002` → ✅）

- 动因：`CYS-PKT-008` 的验收命题「抓包吞吐显著高于 pcap live」从立项起**没有任何数据**。
  上一批刚证明离线路径上限在派发端，捕获侧正是缺证据的一段。
- **结论里有一条否定自己的**：libpcap 1.10 的 live 路径自己就走 `TPACKET_V3` + `PACKET_MMAP`，
  实测三条路径同级（L 11,088,260 包/1.46 s ≈ V 10,126,401/0.99 s ≈ P-v3 10,759,233/1.27 s，
  每包 CPU 均 0.10~0.13 µs）→ **原验收标准设错了对照轴**，已修正为
  「mmap 环显著优于拷贝模式」并实测：零丢包同负载下每包 CPU **5.9~6.3× 更省**（0.13~0.14 vs 0.81~0.82 µs，两次独立复跑）、

  砍到 **1.74×** 之一（165,924 vs 95,450 pps）。
- **丢包可观测做实**：`af_packet::stats()` 现场轮询 `PACKET_STATISTICS` 并**累加**
  （原先只在 `close()` 读一次 → 长跑期间不可见、被信号杀掉就永远丢），与 macOS BPF 的
  `stats()` 语义对齐；CLI 加 `--stats-every`；socket / 设备 / softnet 三类丢包**分开记账**。

  不支持的后端点名拒绝并让 CLI `exit 2` —— 否则对照实验两臂可能跑同一条路径却看不出来。
- 新增 Linux 确定性打流工具 `cythsec-inject`（自报 sent/pps，不引入 pktgen 之类依赖）。
- **修掉 4 个「从未被独立工具检验过」的真 bug**：
  1. 参照程序 `af_packet_capture.c` 把 `tp_mac` 当块内偏移（应相对本帧头）→ `packets=8` 却 `bytes=6.28e9`；
  2. 同文件把 `tp_next_offset` 当块内绝对偏移（应相对当前帧）→ 带负载直接崩；

  `+=` 改 `=` → 「close 后是累加」断言红；去掉 BPF 档位拒绝 → 跨平台不变量红。
- 环境教训（已记入 HANDOFF §7 第 13~15 条）：
  **装在引号串里的脚本，外层 `bash -n` 查不出语法错**（内层引号与外层配平，错误要等容器跑

## 第五段：逐包 → 流级（IPFIX v1 落地）

- **触发**：一句质问 ——「运营商级 netflow 技术栈不用吗，这种抓包怎么可能扛得住省域网这么庞大的流量」。
  当场把量级算清：单条 100G 平均 500 B = **25 Mpps**、最坏 64 B 帧 = **148.8 Mpps**；
  骨干 10 Tbps 全量 = **2.5 Gpps ≈ 108 PB/天**；本仓最强（离线派发端）**2.33 Mpps = 10G 最坏帧的 16%**。
  结论：**逐包全量差 3~5 个数量级，不是"还不够快"而是量级错误**；`CYS-PKT-008` 的定位是
  **单点包级能力**，不是省网采集手段（登记 `CYS-DOC-023`）。
- **缺口核对**：整条链此前出口只有自研 JSONL，`netflow|ipfix|sflow|gnmi` 全仓**零命中** ——
  记录再准也进不了任何真实采集体系。据此登记 **M11「流级遥测与采集」8 项**
  （`CYS-TRF-051/052/053/054`、`CYS-TEL-015`、`CYS-INF-040`、`CYS-PKT-032`、`CYS-DOC-023`），
  总数 375、M11 = 8。
- **落地 v1**（`CYS-TRF-051/052` → ◐）：`src/export/mod.rs`（编码器：报文头/模板集/数据集、
  v4 模板 256、v6 模板 257、模板分族按需携带、序列号只计数据记录、零填充 4 字节对齐）+
  `src/export/sink.rs`（UDP + 落盘 pcap，手写以太/IPv4/UDP 且校验和真算）；
  CLI `--ipfix-udp/-pcap/-domain/-max-msg/-template-refresh`，统计行含 messages/records/bytes/errors。
- **规范核对**（不凭记忆）：IANA IPFIX IE 注册表取表核对 13 个编号；RFC 7011 §3.1 序列号语义、
  §3.3.1 零填充与"填充必须短于记录"；RFC 5103 §6.1 反转 IE = 企业位 + **PEN 29305** + 同编号
  → 双方向 v1 不做（`FlowRecord` 只有总量计数，硬做只能编造方向归属）。
- **验证**：Rust 单测 16 项（含**逐字节手写金标准报文**）；`--rust` 334 lib 项全绿；
  `--ipfix` 门禁 4 样本 × 九类字段逐条相符 + IE 152/153 取 PDML 原始 8 字节比对 +
  UDP 通道字节与 pcap 载荷**逐字节相同** + 5 项产物级反向注入**全部被检出**；`test-all.sh --self-test` 加了 `--ipfix` 工具链映射断言。
  tshark 原始证据：`Version: 10 / Length: 300 / Observation Domain Id: 1`，模板 11 字段逐个解出。
- **踩到的坑（已进 HANDOFF §7 第 16~17 条）**：tshark 的 IPFIX 字段名不能猜
  （`cflow.flow_id`、时间嵌在 `cflow.timedelta_tree`、单模板集的 `template_id` 在子节点）；
  **同一份产物在两个 tshark 版本上渲染不同**（macOS 4.6.9 给 ISO+Z，Rocky 4.4.2 给
  `Nov 15, 2023 …` 本地化）→ **第三方核验必须取原始值（PDML `value=`），不取渲染串** ——
  这条是在 Rocky 测试机复跑时被抓出来的，本机全绿完全掩盖了它；
  **bash 3.2 会把紧跟 `$var` 的全角字符吃进变量名**（中文输出里一律 `${var}`），
  以及 `set -u` 下空数组 `"${arr[@]}"` 报 unbound variable。
## 第六段：IPFIX 采集器（序列号缺口 = 导出丢包率）

- **为什么必须自己做**：导出器只能证明"我发了 N 条"，运营商口径考核的是**"对端收到多少、丢了
  多少"**。RFC 7011 §3.1 把 `Sequence Number` 定义为"本报文之前已发送的**数据记录**累计数"，
  §11.6 明确要求采集进程**必须**跟踪序号发现丢包 —— 也就是说这个指标是协议里留好的观测点，
  不做采集侧就只能自说自话。
- **结构**：把线路格式（IE/模板/常量）抽到 `src/ipfix/mod.rs`，**编码器与采集器共用同一份定义**
  （两侧各写一份会"一起错还互相验证通过"）。新增 `src/ipfix/collector.rs`（约 900 行含 25 项单测）
  + `src/bin/ipfix_collect.rs`（`cythsec-ipfix-collect`，`--pcap`/`--udp`、JSONL 输出、统计行）。
- **按 RFC 落地的语义**：缺口只在前进方向记账、界外按乱序且**不重置基线**（§11.6 点名的注入蒙蔽）；
  首报文无基线不算丢包；模板生存期 = 观测重传间隔 × 3（§8.4）；UDP 上模板撤回**忽略**（§8.4）；
  同模板号不同定义保留旧模板 + 计数（§8.1）；缩减长度编码按实际字节数读（§6.2）。
- **门禁** `check-ipfix-collect.sh`（挂进 `--ipfix`，与导出关口同组）：
  ① 完整回路逐字段相符 **9/9**（五元组/包数/字节数/flowId/起止毫秒）；
  ② **删中间那个 datagram**（5→4，丢 2 条）→ 必须报 `gaps=1 lost_records=2`，
  `loss_ppm=222222` 与独立手算 `2/(7+2)` 一致；③ 无注入必须报 0（否则正向断言恒真）；
  ④ 判定自身 6 项反向注入（含 1 项"必须通过"）全部符合预期。
- **踩到的坑（进 HANDOFF §7 第 18~19 条）**：
  ① 解析 TLV 时"跳过不认识的字段"**必须按长度跳过，不能从字段表里删掉** —— 删掉后后续字段
  偏移整体前移，读出来**仍是合法字节**（octets 变成 `0xAABBCC0000000000`），不崩不报错，
  只有手写期望值的单测能抓；
  ② `std::net::UdpSocket` **没有任何设置 `SO_RCVBUF` 的接口**，零依赖前提下放大收包缓冲做不到 →
  高突发下内核丢的是采集器自己的包，会以缺口形式污染"导出丢包率"，已在 §6 与帮助文本写明。
- **诚实边界**：`loss_ppm` 是导出丢包率（含采集侧丢弃），不是网络丢包率；未与真实网元/异厂导出器
  联调过；TCP/SCTP 的模板隐式撤回、Options Template 未做。
- **本批还修掉一处默认门禁的间歇性假红（`--live` D 项）**：全量 `test-all.sh` 跑出
  `✗ D Rust decode_fail == tshark 前缀非IP帧数: 期望 56，实际 58`，归因行直接给出
  `decode_fail code=decode.non_initial_fragment count=2` —— 抓包窗口里恰好有 2 个**非首片分片**：
  tshark 的 `frame.protocols` 对它们仍写 `eth:ethertype:ip`，而我们**按设计拒绝**（端口在首片里）。
  病根与 §2.7 记的上一次假红完全相同（判据依赖现场流量），修法：裁判口径改成
  「解不出五元组 = 非 IP + IPv4 非首片 + IPv6 非首片」，并把该场景做成**合成 3 帧的完整判定链自证**
  （灌共享环 → ring-consume → `decode_fail`，要求 == 2）。关口从 14 项变 15 项断言。
  另：写夹具时 IPv4 首部少一字节把 `flags+frag` 顶偏、合成帧退化成首片，是**独立期望值**抓到
  的，而"完整判定链"那条**两边一起瞎照样通过** —— 记进 §7 第 20 条。
- **两机复验**：macOS（tshark 4.6.9）+ Rocky 10.2 aarch64（tshark 4.4.2 / python 3.12.13）
  ——`--rust --flows --ipfix` 全绿（回路 9/9、缺口 2 条与手算一致、6/6 注入判红），
  `--live` 两机均 15 项断言通过（含新增的合成非首片分片完整判定链自证）。
## 第七段：采集集群容量模型（CYS-INF-040）

- **为什么做**：对外被问的是"省网量级你们怎么采"，正确答案不是"采得完"，而是把算式摊开。
  算式：`链路包率 = 带宽÷(平均包长×8)` → `记录率上界 = 包率÷采样率` → `台数 = ceil(记录率÷(每台×余量))`
  → `TB/天 = 记录率×86400×每条字节`。
- **主算例**：20 Tbps / 1:1000 / 500 B ⇒ 5 Gpps → 5 Mpps → **5 Mrec/s → 2 台 → 17.28 TB/天**。
- **三档分解**（同一 20 Tbps）：核心 8T@1:1000 = 2.0 Mrec/s、汇聚 8T@1:500 = 4.0、接入 4T@1:100 = 10.0
  ⇒ 合计 **16 Mrec/s / 7 台 / 55.3 TB/天**。**采样率是分层的，出口那一档不能代表全网**（差 3 倍）。
- **每台容量必须有出处**：`cythsec-bench` 新增 `ipfix-collect-decode`（用生产编码器造语料、
  只对解码计时、断言"所有记录都被交付"），M1 Pro release 实测 **4.7 Mrec/s**；门禁用例数 19→20。
- **脚本**：`scripts/plan/collector-capacity.py`，挂 `test-all.sh --plan`（新分组，纯 python3 秒级，
  进默认集合）；`--json` / `--from-bench`（吃实测值）/ `--tiers`（替换三档假设）；
  `--self-test` 用手算期望值 + 3 项反向注入（漏除采样率、丢余量系数、比特当字节）+ 台数边界
  （恰好打满=1 台、多一条=2 台）。
- **三个必带口径**：① 采样率（规划值，真采样待 `CYS-TRF-053`）② 导出丢包率（`CYS-TRF-054` 的 `loss_ppm`）
  ③ 采集覆盖率（**待部署清单填**；缺省 100% 是规划口径不是事实）。
- **留着的假设**：落盘 **40 B/记录未实测**（直接决定 TB/天）—— 这是容量表里最后一个假设，
  已记入 §6 与下一棒；每台容量是单机实测，换机器要 `--from-bench` 重算。
## 第八段：口径修正（CYS-DOC-023，已闭环）+ 两机复验

- **两条路径各一句判定句**：包级「要求逐包全量留存 ≥ 1 Tbps 即量级不成立」；流级「三个口径都能给出具体数字即可算并可复算」。
- **算式写进脚本而非只写文档**：新增「逐包全量 vs 流级」对照段 —— 10 Tbps 全量 = 108 PB/天，
  1:1000 流级 = 8.64 TB/天，**倍数 12,500 = 4.1 个数量级**（原文档说"差 3~5 个数量级"，现在有算法）。
  自证算例 G 用手算值钉住这三个数：量级结论最容易被口耳相传记错一位数。
- **两机复验**：Rocky 2 vCPU 上 `--plan --rust --ipfix --flows` 全绿（rc=0）；

## 第九段：异厂导出器互操作（CYS-TRF-054 ④ 的离线替代）

- **动因**：仓库两个 IPFIX 关口（导出 vs tshark、导出→采集回路）里，编码器与采集器
  **共用 `src/ipfix/mod.rs` 的同一份模板定义** —— 定义读错 RFC 时两边一起错、回路照样绿。
- **做法**：`scripts/verify/interop-ipfix.py` 是一个只读 RFC 7011 手写的独立实现
  （模板 ID 4001~4004 / 字段序相反 / 观测域 0x1234ABCD / 计数器缩减长度编码 /
  夹带未登记 IE 9999,12345 / options template set / 模板撤回 / 同号不同定义重定义 /
  先数据后模板 / 零填充），+ `check-ipfix-interop.sh` 驱动（挂 `--ipfix`）。
  5 场景逐条对**手写常量**；tshark 再确认这份报文本身合法（8 字节与 4 字节两种编码
  必须解出同一串 octets）；判定自身 6 项反向注入。
- **当场抓到的两件事**：① CLI 统计行漏印 6 个联调字段（`template_conflicts` /
  `withdrawals_ignored` / `options_template_sets` / `nonzero_padding` / `records_missing_key` /
  `templates_refreshed`）——结构体有、命令行看不到；② `unknown_ies=6`：IE 6 是 IANA 登记的
  `tcpControlBits`，真实导出器都会发，而我们按长度跳过、不取值（能力边界，已记 §6）。
- **新口径边界**：模板缺失时 `loss_ppm` 是**上界**（模板未知 ⇒ data set 里有几条记录不可知 ⇒
  下一报文的序号差被算成 lost_records；§11.6 要求的严格读法）。互操作关口把它钉死：
  `no_template_sets=1` ⇒ `lost_records=2` / `loss_ppm=285714`。
- **写测试时自己踩的坑（都靠手写期望值抓到）**：d8 的序列号写成 7（应为 5，多算一个缺口）；
  `records` 是"解出来的条数"不是"导出侧发的条数"；重发同一条记录会被去重窗口正确丢掉
  （第一版把 3 条重发当成 3 条新记录）；`expect_tup` 漏写 proto，报错信息是"两个看起来一模一样的
  元组不相等"——已让 `len(tup)!=5` 直接抛错。
- **两机复验时踩的坑（值得记）**：关口原先假定 `target/debug` 里的采集器是当前源码构建的，
  在 Rocky 上跑红了 5 个场景 —— 红的原因是那台机器上的二进制还是"加统计字段之前"的旧产物。
  判据要断言的是**当前源码**的行为，故守卫里显式 `cargo build --offline`；
  cargo 缺失时退出 3（未核验），**不静默退回旧产物**。tshark 4.4.2（Rocky）与 4.6.9（macOS）
  对同一份异厂语料给出完全一致的 `cflow` 字段与 octets。
## 第十段：落盘字节/记录实测（CYS-INF-041）

- **动因**：容量表（§2.13）里每个参数都有出身，唯独「落盘 40 B/记录」是列式压缩的规划假设，
  而它直接决定 `TB/天`（要买多少盘）。
- **做法**：`scripts/plan/measure-storage.py` 吃 `cythsec-analyze` 产出的真实 `FlowRecord` JSONL，
  给未压缩/gzip 两档字节数与"字节花在哪"（实测 features 占 43%、app 17%）；`--combine` 合成规划值
  （**两档各取较差端**）；产物固化在 `docs/planning/measurements/`（含样本量、gzip 工具版本、方法）。
  接线：`collector-capacity.py` 默认读产物 gzip 档 + 新增 `--verify-defaults`（内置默认值 ↔ 产物必须一致）。
- **实测结论**：真实向量语料 37 条 ⇒ 1008.3 / **79.4 B/记录**（gzip）；同质压测语料 20,182 条 ⇒

  三档合计 55.3 → **109.73**、逐包全量/流级倍数 12,500 → **6,297**（4.1 → 3.8 个数量级）。
- **可证伪**：自证 = 手算字节数 + 末行无换行计数 + **gzip 往返校验** + TB/天手算 + 空语料抛错；
  5 项注入（漏算换行/压缩档上报未压缩/字节当比特/条数多 1/合并取最好看一端）全部判死；
  容量模型加算例 H + 注入 `trust-planning`（假装读了产物、用回旧 40 B）⇒ 33.5664 变 17.28 判死。
- **两机复验（重要）**：同一份 37,306 B 语料，macOS **Apple gzip 487.0.1** 与 Rocky **GNU gzip 1.13**
  输出字节数**完全相同**（2,937 B ⇒ 79.4 B/记录）。我原先在文档里写了"不同实现会有微小差异"——
  这是**没量就写下的预设**，量完必须改掉（留着会让人以为数字不可复现）。真正要写清的是**方法**：
  文件参数 vs stdin 管道差 20 B（文件名/时间戳头），那才是复现时容易踩的坑。
## 第十一段：流级采样（CYS-TRF-053）—— 声明与执行必须一致

- **动因**：IPFIX 的 IE 34（`samplingInterval`）是一句对外承诺（"计数是每 N 个包采 1 个，
  还原量级就乘 N"）。声明 1:1000 却没真丢包 ⇒ 采集侧把采样流量当全量，容量模型/丢包率全错。
- **落地**：`--sample 1:N`（默认 1）+ `--sampling-mode flow|packet` + `--sampling-seed`。
  `flow`（默认）按**流键哈希**决定（同一条流全采或全不采、与包序无关 —— 逐包随机采会把一条
  会话撕成半条，状态机跳号/重组缺片，产出的记录**看起来正常但结论是错的**）；采样决定在
  **派发端**做（放 worker 会让实际采样率放大 N×）；IE 34 取自**同一份配置**（**刻意不做**
  `--ipfix-sampling`：一个开关声明、另一个开关执行 = 把撒谎的入口留在代码里）；导出计数
  **不放大**（×N 还原是采集侧的事，乘系数等于用假设伪造测量值）。
- **顺手抓到的真实缺陷**：`ExportConfig.sampling_interval` 被**硬编码忽略** —— 有字段、有校验、
  有文档，`write_record` 里却是 `&1u32`。"配置项看起来在做事、实际什么也没做"。修法：接线 +
  单测 `sampling_interval_is_written_into_records`（配置 1000 与默认 1 两个方向）。
- **可证伪**（`test-all.sh --sampling`，关口自己构建二进制；缺 cargo/tshark 退 3 未核验）：
  自造 400 条流 1:4 → 留存 107（手算 100±12）；被采到的流除 `session_id` 外与不采样**逐字段相同**；
  tshark 读 IE 34（不采样全 1 / 1:4 全 4，且条数==留存流数）；`--workers 4` 与 1 一致；
  `packet` 模式 800 包留 200；3 项**真实**注入（`keep-all` 采样器没接上 / `torn-flows` 逐包却
  自称 flow / `no-ipfix` 声明未落线）全部判红。
- **两个自证写法上的教训**：① 第一版"注入"只是拿错值去比（tautology），改成 `--inject` 真的改变
  那次运行再跑正常断言 —— **注入必须改变被测行为，不能只是换个期望值**；② 完整性断言第一版
  把 `session_id` 一起比了，于是 107 条全"不同"——它是每次运行的序号（采后只给被采到的流编号），
  必须**显式排除并写明理由**，而不是放宽整条断言。

  `CYS-PKT-032`；当前采样点只在流键上，故只能用于离线重放）→ 真实网元联调。 → 落盘压缩比实测（消掉最后一个假设）→ `CYS-TRF-053` 采样 → 与真实网元/异厂导出器联调（20 Tbps×1:1000 → 采集器台数/TB 每天，可复跑脚本）→
