## 2026-10-05 采集侧收口：mmap 环 vs 拷贝模式对照实测（`CYS-PKT-008` → ✅、`CYS-CAP-002` → ✅）

- 动因：`CYS-PKT-008` 的验收命题「抓包吞吐显著高于 pcap live」从立项起**没有任何数据**。
  上一批刚证明离线路径上限在派发端，捕获侧正是缺证据的一段。
- **结论里有一条否定自己的**：libpcap 1.10 的 live 路径自己就走 `TPACKET_V3` + `PACKET_MMAP`，
  实测三条路径同级（L 11,088,260 包/1.46 s ≈ V 10,126,401/0.99 s ≈ P-v3 10,759,233/1.27 s，
  每包 CPU 均 0.10~0.13 µs）→ **原验收标准设错了对照轴**，已修正为
  「mmap 环显著优于拷贝模式」并实测：零丢包同负载下每包 CPU **5.9~6.3× 更省**（0.13~0.14 vs 0.81~0.82 µs，两次独立复跑）、
  饱和时同机端到端速率 **1.35×**、真实网卡（`enp2s0`，放开 `rmem_max`）拷贝档把整机容量
  砍到 **1.74×** 之一（165,924 vs 95,450 pps）。
- **丢包可观测做实**：`af_packet::stats()` 现场轮询 `PACKET_STATISTICS` 并**累加**
  （原先只在 `close()` 读一次 → 长跑期间不可见、被信号杀掉就永远丢），与 macOS BPF 的
  `stats()` 语义对齐；CLI 加 `--stats-every`；socket / 设备 / softnet 三类丢包**分开记账**。
- **采集档位 `--capture-mode auto|v3|v2|recvfrom` 指定即严格**：失败报错不降级，
  不支持的后端点名拒绝并让 CLI `exit 2` —— 否则对照实验两臂可能跑同一条路径却看不出来。
- 新增 Linux 确定性打流工具 `cythsec-inject`（自报 sent/pps，不引入 pktgen 之类依赖）。
- **修掉 4 个「从未被独立工具检验过」的真 bug**：
  1. 参照程序 `af_packet_capture.c` 把 `tp_mac` 当块内偏移（应相对本帧头）→ `packets=8` 却 `bytes=6.28e9`；
  2. 同文件把 `tp_next_offset` 当块内绝对偏移（应相对当前帧）→ 带负载直接崩；
  3. 同文件 pcap 全局头 `ver_major/ver_minor` 各写成 4 字节（应各 2 字节）→ 整块后移 4 字节，
     `network` 字段读出来是 snaplen（tshark: `network type 2112 unknown`）——
     **`CYS-CAP-002` 的「产物可被 Wireshark 打开」此前其实不成立**；
  4. 对照脚本：ping 洪泛被 kill 就没有分母（`offered=0`）、打流被 kill 就没有自报、
     测量顺序（先打流后抓包 → 头 0.5 s 落在无监听窗口，凭空 5% 残差）。
- **反向注入三条**（都实测）：去掉 `stats()` 的运行中轮询 → 「close 前可读」两条断言红；
  `+=` 改 `=` → 「close 后是累加」断言红；去掉 BPF 档位拒绝 → 跨平台不变量红。
- 环境教训（已记入 HANDOFF §7 第 13~15 条）：
  **装在引号串里的脚本，外层 `bash -n` 查不出语法错**（内层引号与外层配平，错误要等容器跑
  几分钟才炸，本轮白等两次）→ 内层脚本独立成文件、外层先 `-n` 再 `bash -s` 喂进去；
  **`SO_RCVBUF` 会被 `net.core.rmem_max` 静默削顶**（请求 4 MiB 只给 416 KiB）而
  `PACKET_RX_RING` 不受限 → 设置内核资源上限后必须 `getsockopt` 回读并如实报出。
- 验证：Linux 测试机 `--cpp` **7/7**（新增 `packet_engine_capture_modes`）、`--rust` 342 全过、
  `--live` 真机真网卡 **14/14**；macOS `--cpp` 6/6；lint 全过。
- **未达成**：物理网卡上的**线速**对照（真实网卡那臂是 TX→tap、且 2 vCPU 虚机，绝对数不可比）；
  macOS 侧真抓包仍需一次免密 sudo 现场。

## 第五段：逐包 → 流级（IPFIX v1 落地）

- **触发**：一句质问 ——「运营商级 netflow 技术栈不用吗，这种抓包怎么可能扛得住省域网这么庞大的流量」。
  当场把量级算清：单条 100G 平均 500 B = **25 Mpps**、最坏 64 B 帧 = **148.8 Mpps**；
  骨干 10 Tbps 全量 = **2.5 Gpps ≈ 108 PB/天**；本仓最强（离线派发端）**2.33 Mpps = 10G 最坏帧的 16%**。
  结论：**逐包全量差 3~5 个数量级，不是"还不够快"而是量级错误**；`CYS-PKT-008` 的定位是
  **单点包级能力**，不是省网采集手段（登记 `CYS-DOC-023`）。
- **缺口核对**：整条链此前出口只有自研 JSONL，`netflow|ipfix|sflow|gnmi` 全仓**零命中** ——
  记录再准也进不了任何真实采集体系。据此登记 **M11「流级遥测与采集」8 项**
  （`CYS-TRF-051/052/053/054`、`CYS-TEL-015`、`CYS-INF-040`、`CYS-PKT-032`、`CYS-DOC-023`），
  总数 375、M11 = 8。
- **落地 v1**（`CYS-TRF-051/052` → ◐）：`src/export/mod.rs`（编码器：报文头/模板集/数据集、
  v4 模板 256、v6 模板 257、模板分族按需携带、序列号只计数据记录、零填充 4 字节对齐）+
  `src/export/sink.rs`（UDP + 落盘 pcap，手写以太/IPv4/UDP 且校验和真算）；
  CLI `--ipfix-udp/-pcap/-domain/-max-msg/-template-refresh`，统计行含 messages/records/bytes/errors。
- **规范核对**（不凭记忆）：IANA IPFIX IE 注册表取表核对 13 个编号；RFC 7011 §3.1 序列号语义、
  §3.3.1 零填充与"填充必须短于记录"；RFC 5103 §6.1 反转 IE = 企业位 + **PEN 29305** + 同编号
  → 双方向 v1 不做（`FlowRecord` 只有总量计数，硬做只能编造方向归属）。
- **验证**：Rust 单测 16 项（含**逐字节手写金标准报文**）；`--rust` 334 lib 项全绿；
  `--ipfix` 门禁 4 样本 × 九类字段逐条相符 + IE 152/153 取 PDML 原始 8 字节比对 +
  UDP 通道字节与 pcap 载荷**逐字节相同** + 5 项产物级反向注入**全部被检出**；`test-all.sh --self-test` 加了 `--ipfix` 工具链映射断言。
  tshark 原始证据：`Version: 10 / Length: 300 / Observation Domain Id: 1`，模板 11 字段逐个解出。
- **踩到的坑（已进 HANDOFF §7 第 16~17 条）**：tshark 的 IPFIX 字段名不能猜
  （`cflow.flow_id`、时间嵌在 `cflow.timedelta_tree`、单模板集的 `template_id` 在子节点）；
  **同一份产物在两个 tshark 版本上渲染不同**（macOS 4.6.9 给 ISO+Z，Rocky 4.4.2 给
  `Nov 15, 2023 …` 本地化）→ **第三方核验必须取原始值（PDML `value=`），不取渲染串** ——
  这条是在 Rocky 测试机复跑时被抓出来的，本机全绿完全掩盖了它；
  **bash 3.2 会把紧跟 `$var` 的全角字符吃进变量名**（中文输出里一律 `${var}`），
  以及 `set -u` 下空数组 `"${arr[@]}"` 报 unbound variable。
